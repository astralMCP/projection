# PRD — Projection

**A TypeScript library that wraps any MCP server in code mode (LLM-authored XState workflows) and a tool catalog (search, describe, call), with human-approved side effects, built on MCP 2026-07-28 MRTR and XState.**

Status: Living requirements, implemented through the current release · Package: `@astral-mcp/projection` (npm) · Target spec: MCP 2026-07-28 (final)

"v1" in this document means the scope the PRD commits to, not a package version (the package is 0.x).

---

## 1. Summary

Projection wraps an existing MCP server (or a remote connection to one) and exposes two small projections of it: **code mode** — `execute_machine`, which runs an LLM-authored XState v5 state machine inside a QuickJS WebAssembly sandbox, and `discover_apis`, which returns generated TypeScript type definitions describing the wrapped server's tool API — and the **catalog projection** (`search_tools`, `describe_tool`, `call_tool`). Five tools in all, never the wrapped server's own. One facade can also front several servers as **tool boxes** under integrator-chosen aliases, with qualified tool names (`<alias>.<name>`) and one search tool per box (§6.9). A remote server can be given by URL alone: when it requires authorization, Projection asks the user to sign in the first time a request needs it and keeps the tokens in the OS credential store (§6.10).

The machine orchestrates calls to the wrapped server's tools. Read-only tool calls execute immediately. Any non-read-only tool call suspends the machine, serializes its snapshot into a sealed opaque blob, and returns an MRTR `InputRequiredResult` asking the human to approve the action. When the client retries the call with the approval and the echoed `requestState`, the library rehydrates the machine from the blob and continues exactly where it left off.

Because all suspension state travels in the MRTR payload, the library is fully compatible with stateless, horizontally scaled deployments: any server instance can resume any workflow.

Alongside code mode, the same facade exposes a **catalog projection** (§6.8): `search_tools`, `describe_tool` and a polymorphic `call_tool` for single actions and for servers whose tool surface is too large to describe up front. Both projections run through one policy engine, one approval path and one blob sealer, so a direct call is gated exactly like a step inside a machine.

## 2. Background and motivation

The code-mode pattern (one execute-code tool instead of N tools) reduces context bloat, lets models compose multi-step workflows in a single call, and keeps intermediate data out of the model's context. Its historical weakness is side-effect safety: once code is running, every write it performs is invisible until it is done.

MCP 2026-07-28 removes that weakness. The spec is stateless at the protocol core, and Multi Round-Trip Requests (MRTR, SEP-2322) let a `tools/call` return `resultType: input_required` with a map of `inputRequests` (elicitation or sampling requests) and an opaque `requestState` blob. The client gathers answers and re-issues the original call — original arguments included — with `inputResponses` and the echoed state. This gives us, for free: (a) mid-execution human approval without holding a stream open, (b) the original code re-delivered on every resume, and (c) a spec-blessed vehicle for carrying serialized machine state.

XState v5 is the execution substrate because its actors are designed to be persisted and restored (`getPersistedSnapshot()` / `createActor(machine, { snapshot })`), because explicit states make write actions statically auditable, and because denial of an approval becomes an ordinary transition the machine can handle gracefully.

## 3. Goals

G1. Wrap any MCP server — from a server class instance in-process, or from a remote server via `tools/list` introspection — or several of them behind one facade, into code mode and a tool catalog with no changes to the wrapped servers.

G2. Execute LLM-authored XState v5 machines (JS or TS) in an isolated QuickJS sandbox with hard resource caps.

G3. Gate every non-read-only tool invocation behind an MRTR elicitation approval, with suspend/resume carried entirely in the signed, encrypted `requestState` blob.

G4. Operate correctly on stateless infrastructure: no server-side session store, no sticky routing; any instance can resume any suspended workflow.

G5. Provide a fast reactive self-healing loop: malformed or invalid code returns structured `isError` results rich enough for the model to correct and retry, with no host-side type checking in the hot path.

G6. Ship a `discover_apis` tool that returns generated `.d.ts` files and the authoring contract so the model can write correct code on the first or second attempt.

## 4. Non-goals

N1. No host-side TypeScript type checking before execution (explicitly rejected for latency; see G5).

N2. No general-purpose plain-JS execution mode in v1. The only accepted program shape is an XState v5 machine conforming to the authoring contract.

N3. No network access from the sandbox. `fetch` is never injected, regardless of configuration.

N4. No durable server-side persistence of workflow state. State lives in the blob or nowhere.

N5. MCP Apps rendering beyond the static workflow dashboard (approval previews, SSR) is a stretch goal (§12.1).

N6. No filesystem surface for authored code in v1 (see R9, §12.3), and no mid-run sampling requests (deprecated; see Q2).

## 5. Users

The **integrating developer** installs the library, points it at their MCP server (or several, each under an alias they choose), and configures policy and limits. The **model** (any MCP client's LLM) calls `discover_apis`, authors a machine, and calls `execute_machine`, self-correcting from structured errors — or, for a single action, finds the tool with `search_tools`/`describe_tool` and runs it with `call_tool`. The **end user** sees approval prompts rendered by their MCP client from our elicitation requests and approves or declines individual actions, and signs in to an upstream server the first time a request needs it (§6.10).

## 6. Product requirements

Requirement numbers are stable identifiers, not an ordering; R29–R31 sit with the section they belong to.

### 6.1 Exposed tool surface

R1. The library exposes two projections of the wrapped server over one facade, both on by default: **code mode** (`execute_machine`, `discover_apis`) and the **catalog projection** (`search_tools`, `describe_tool`, `call_tool`; §6.8). The integrating developer MAY disable either projection: `WrapOptions.projections?: { codeMode?: boolean; catalog?: boolean }`, each default `true`; both `false` is a `terminal` `ProjectionError` at wrap time (every other wrap-time configuration mistake is a `validate` error, §6.9). The wrapped server's own tools MUST NOT be passed through to the client: `call_tool` is a mediated entry point that validates, applies policy and binds approval to the exact call, never a pass-through. **Direct listing** (`projections.direct?: 'auto' | boolean`, default `'auto'`; D28): with the catalog projection on, the facade may also list each wrapped tool as a **mediated tool** of its own — the tool's name on a single-server facade, `<alias>__<tool>` on a multi-server facade, mapped onto `[A-Za-z0-9_-]{1,64}` with a hash suffix on a collision, so it never shadows a Projection tool — which is a thin alias of `call_tool({ name, args })` under the same gate: validation, policy, approval prompt, sealed blob, replay check and result shape are `call_tool`'s (R35), and its description leads with the posture (R33) above the server's neutralized text. Under `'auto'` the tools are listed when their estimated definitions (name, title, description and sanitized input schema, at 3.5 characters per token) fit `projections.directBudgetTokens` (default 8 000); on a multi-server facade the budget is filled box by box, smallest box first, and the boxes that do not fit keep the search path (R43). `true` lists every tool whatever the size; `false` never lists them, leaving the five-tool surface. `'auto'` stays off when the catalog projection is off; `true` with `catalog: false`, any other value, and a budget that is not a non-negative whole number are `validate` errors. When every tool is listed, `search_tools` is not served (R32). The facade also serves the `projection://` resources (R3) and two prompts (prompts: code mode only), `save-workflow` and `visualize-workflow` (D8). On a multi-server facade the catalog projection adds one `search_<alias>` per box (R43) and the resources add one box overview per box (R45); nothing else is added beyond the mediated tools of direct listing.

R2. `execute_machine` accepts `{ code, lang?, input? }`. `lang` defaults to `"js"`; TypeScript syntax requires `lang: "ts"` (transpiled, not type-checked, R10). `input` is passed as the machine's input. A completed run returns `structuredContent { output, approvals, logs }`, where `approvals` is the audit trail `[{ callId, tool, args, decision: auto | approved | declined | denied_by_policy | error, reason? }]`, plus a text rendering of `output` and any console output; on a multi-server facade each entry's `tool` is qualified (R40). The tool also carries `_meta.ui.resourceUri` for MCP Apps hosts (D5). The description MUST summarize the authoring contract and point to `discover_apis`.

R3. `discover_apis` returns a compact inline overview (pinned XState version, allowed imports, the tool-call event protocol, serializability rules) plus one `resource_link` content block per artifact: `tools.d.ts`, the authoring contract (`projection://docs/authoring-contract.md`) and the example machines (`happy-path.ts`, `denial-fallback.ts`). The server declares the `resources` capability and serves these at stable URIs (`projection://types/tools.d.ts`, `projection://examples/denial-fallback.ts`, …, and on a multi-server facade `projection://boxes/<alias>/overview.md` for each box whose server sends `instructions`, R45) via `resources/read`, letting the model pull full contents only when it wants them. The facade also serves `ui://projection/dashboard.html` (D5), which `discover_apis` does not link. Cache hints are not set; the SDK default (`ttlMs` 0) applies. The inline overview MUST be sufficient to author a simple machine unaided, so clients with weak resource support still function. On a multi-server facade the overview's tool list is grouped per box (R45).

R4. Types are generated from the wrapped server's `tools/list` JSON Schemas. An in-process `McpServer` is introspected over an in-memory transport exactly like a remote `Client`, so there is one path (a hand-rolled JSON Schema → TypeScript converter that degrades unsupported constructs to `unknown`). Tool names are namespaced into a single `tools` API surface importable as `@astral-mcp/tools`. On a multi-server facade each box's tools sit under `tools.<alias>` (R45).

R29. The library forwards the wrapped server's `instructions` field verbatim, then appends a short (2–3 sentence) preamble that states the **routing rule** between the two projections: a single action goes through `call_tool` (with `search_tools` to find the tool — a query's top hits show their arguments, R33 — and `describe_tool` for any other tool's); several steps, branching on results, computing over a list (counting, filtering, summing, comparing or checking every item, so the model does not do arithmetic by hand over a large result, D29), or a workflow worth saving are authored as a state machine and run with `execute_machine` (after `discover_apis`); and either way a tool that changes something may pause for user approval, with each tool's listing giving its posture (R33). When a projection is disabled the preamble describes only the one that is on. When direct listing lists the tools (R1, the default for a small catalog), the preamble says instead that the server's tools are listed directly and are called by name with no need to search or describe them first, then keeps the routing rule: a single action or a short chain is called one tool at a time, `execute_machine` is for work that loops or branches, computes over a list, takes many steps or is worth saving. The preamble is library-supplied copy, overridable by the integrating developer (`codeModePreamble` replaces the whole preamble, whichever projections are on). On a multi-server facade the wrapped servers' instructions are not forwarded; R44 replaces them with a shelf of boxes, and the preamble names the search tools the facade serves (R43).

R30. The internal tool catalog, generated types, and blob format MUST NOT assume a single wrapped server. The catalog is keyed by server alias: a single-server facade (`wrapMcpServer`) uses the default alias, omitted from tool names and generated type paths for ergonomics; a multi-server facade (§6.9) uses the integrator's aliases. The blob records the server identity it was minted against (R41 on a multi-server facade; for a source given by URL, its canonical URL, R60), and a tool name recorded in the blob carries its alias (R40), so multi-server facades need no blob-format break.

### 6.2 Authoring contract (what the LLM must write)

R5. The submitted module's top level MUST only define and default-export a machine created with XState v5 `setup(...)`/`createMachine(...)`. A tool call requested at module top level is rejected (phase `validate`), because the module is re-evaluated from the re-sent `code` argument on every resume.

R6. Machine `context` MUST be JSON-serializable at all times. Validation round-trips a snapshot through JSON to enforce this before first execution. Only the initial context is probed; a non-JSON value introduced later is not detected and degrades at seal time under JSON semantics (`undefined` and functions dropped, `Date` to string, `Map`/`Set` to `{}`).

R7. Tool calls MUST NOT be modeled as invoked promise actors (any `invoke` in the machine config is rejected at validation — restored snapshots restart invoked actors, which would re-execute approved writes). Instead, the contract provides a library-supplied action creator: the machine emits `toolCall(name, argsFromContext)` and waits in a state for `TOOL_RESULT`, `TOOL_ERROR`, or `TOOL_DENIED` events. The host — not the machine — performs all I/O. Every result event carries the call's `callId` and `args`, the arguments of the call it answers (for an approved call, the sealed ones that executed or were declined; D31); `toolCall` accepts `{ id }` and the bridge exports `whenCall(id)`, a guard for machines with several calls outstanding (parallel regions), because XState delivers an event to every region that can handle it. `toolCalls(name, argsList, { id }?)` requests one call per item of a list (or of a function of the action arguments returning one) from one action, ids `<id>#0`, `<id>#1`, … in list order (`<id>` defaults to the tool name), so the calls are outstanding together and the gated ones share one round trip (R15); every item is checked like `toolCall`'s arguments before any is queued, and an empty list requests nothing. `whenCallIn(id)` guards every event whose `callId` starts with `<id>#`; a machine matches an event to its item by `event.args`, since events need not arrive in list order (an R15a error answers in the first segment, the approved calls after the round trip). Two gated calls in flight under one id are a `validate` error, not one sealed entry. Authoring contract rule 5 teaches the pattern, quoting the facade's `maxRoundTrips` (D30). On a multi-server facade `name` is qualified (`toolCall('<alias>.<name>', args)`, R40) and the host routes the call by alias (R45).

R8. The sandbox mounts a pinned XState v5 build at `xstate` and the generated bridge at `@astral-mcp/tools`. The only other specifiers that resolve are the pure utilities the QuickJS runtime boots with — `buffer`, `util`, `url` and the `@node_compatibility/*` shims (`event-target`, `headers`, `request`, `response`) — none of which perform I/O; every other import fails at validation with a structured error. The authoring contract tells models only `xstate` and `@astral-mcp/tools` resolve.

R9. No filesystem surface is exposed to authored code in v1. The sandbox mounts only what the library itself needs internally (module resolution for `xstate` and `@astral-mcp/tools`); `node:fs` imports and FS access from authored code fail at validation. The authoring contract states plainly: all working state lives in machine context. Scratch FS is a stretch goal (§12.3).

### 6.3 Execution engine and resource caps

R10. Execution uses `@sebastianwessel/quickjs` (quickjs-ng WASM variants). TypeScript input is transpiled on the host with the TypeScript compiler API (syntax only, `ts.transpile`) before the VM starts; there is no type checking (G5, N1).

R11. `allowFetch` is hard-disabled. This is an invariant, not a configuration default: the tools bridge is the only I/O channel, otherwise the approval gate is bypassable via arbitrary HTTP.

R12. Default resource caps, all configurable downward and clamped at the stated maxima:

| Cap                                                     | Default | Hard max |
| ------------------------------------------------------- | ------- | -------- |
| Wall-clock per execution segment (per round trip)       | 30 s    | 60 s     |
| WASM memory                                             | 128 MB  | 256 MB   |
| Submitted code size                                     | 128 KB  | 256 KB   |
| Machine input (JSON serialization size)                 | 128 KB  | 256 KB   |
| Auto-run (policy `auto`) tool calls per segment         | 50      | 200      |
| MRTR round trips per workflow                           | 8       | 16       |
| Events delivered by the host to the machine per segment | 10 000  | 50 000   |
| Final result payload                                    | 256 KB  | 1 MB     |
| Machine state nodes (static count at validation)        | 100     | 1 000    |
| Captured console output per segment                     | 64 KB   | 256 KB   |

Values below a small floor (e.g. 1 round trip, 100 ms) are clamped up so a misconfiguration cannot disable the flow; non-finite values are ignored. The auto-run call cap's `cap_exceeded` message breaks the segment's executed calls down by tool, most-called first and at most five tools — `— so far: 50 calls to "<tool>" (all failed, first error: "<message>")` — with the first error neutralized, capped at 200 characters and quoted (S5); when every call to the most-called tool failed, the hint says repeating it will not get further (D29). The WASM memory cap bounds the sandbox's real linear memory — each session owns a WebAssembly memory whose `maximum` is the cap (D15) — and its floor is the module's 16 MB initial heap.

R13. Interrupt handlers enforce the wall-clock budget inside the VM (not only around it), so tight loops cannot outrun the host timer. Each MRTR resume gets a fresh segment budget.

### 6.4 Approval policy and MRTR flow

R14. Default policy derives from tool annotations on the wrapped server: `readOnlyHint: true` → execute immediately; annotation absent or `readOnlyHint: false` → require approval. Annotations are hints from a possibly third-party server, so the integrating developer can override per tool with `auto`, `ask` or `deny`; an override always wins and an unrecognized value fails safe to `ask`. Overrides are read once, at wrap time. Policy is re-evaluated on every resume and outranks a stale approval: a tool that is `deny` when the retry arrives yields `TOOL_DENIED` (machine) or `{ status: "denied_by_policy" }` (`call_tool`) whatever the user answered (D9). `destructiveHint: true` tools SHOULD render with stronger warning language in the elicitation. An approvals mode (R49, `WrapOptions.approvals`, per source on a multi-server facade) can let a non-read-only tool that explicitly declares `destructiveHint: false` run without approval; a per-tool override still wins over it. On a multi-server facade overrides are keyed by qualified names and policy resolves per qualified tool (R42).

R15. On suspension, the library returns `resultType: input_required` with one elicitation entry per pending tool call. When the machine reaches a state (including parallel states) with multiple pending gated calls, all of them MUST be batched into the single `inputRequests` map for one round trip. Opt-in `WrapOptions.approvalPrompts: 'batched'` (default `'per-call'`) puts a suspension holding 2 to 10 calls, whose batched message fits 20 000 characters, to the person as ONE elicitation (key `projection:approvals`): a header, each call's R16 copy under `[k]`, and a form with one boolean `approve_k` per call (no `default`, not `required`) plus the optional `reason`; above either cap it falls back to per-call prompts. The pending map and its per-call sealing are unchanged (S2): call k runs only when `approve_k` is exactly `true` in an accepted answer; any other answer declines it (R17). The layout is sealed in the blob (R20 `prompts`) and the resume answers by the sealed value, never by the resuming instance's option or anything the client sends. A machine makes many gated calls in one suspension with `toolCalls` (R7, D30), and each resumed event carries the sealed `args` of its call (D31): no cap counts the calls one suspension holds; it is bounded by the R23 blob ceiling, and the calls that run without approval by `maxReadCallsPerSegment` (R12), both structured errors. Machine `toolCall` ids starting with `projection:` are a `validate` error (that namespace holds Projection's own input-request keys). A malformed option value fails the wrap (`validate`). Forwarded server questions (R64) in the same suspension are not batched: each stays its own elicitation keyed `upstream-<n>` beside the batched prompt, and its answer approves nothing. `call_tool` suspensions are never batched (one call; R64's `upstream_input` blob has none pending), so neither blob kind carries `prompts`. DECISIONS D25.

R15a. A gated call whose arguments fail the R35.1 structural check is never put to the person: `call_tool` returns the `validate` error (R35.1), and a machine step receives `TOOL_ERROR` with the same message (prefixed `toolCall`), audited as `error`, before any suspension.

R15b. Copy after a refusal (D25). A declined `call_tool` result says the refusal covers only that call; not to make it again or reach its result another way, unless the person's note asks for a change (then make the changed call, which asks again); to carry on with parts of the task that do not depend on it, skipping anything that only makes sense if it had run; and to say in the final answer what was not done. A completed `execute_machine` result whose audit holds declined or policy-denied calls restates them (tool, arguments, note) in a text block after the output, with the same guidance; an `isError` result of a workflow that had decided gated calls also lists the approved calls that already ran, so they are not asked for again. That holds for every failure after the first suspension, those raised while building the next suspension included (the R18 round-trip cap, an unknown tool, a question that cannot be forwarded, a blob over the R23 ceiling).

R16. Each elicitation MUST present a CONCISE, human-readable summary aimed at a non-technical approver: a headline `Approve: <action>` (prefixed ⚠, with a plain warning line, for destructive tools), where the action is the tool's annotation title, else its humanized id, suffixed for method-dispatched tools with the enum-constrained `method`/`action` argument value (e.g. `Create or update issue — create`); the first sentence of the tool description, quoted and attributed ("What the server says it does: …"); the call's arguments after the redaction hook as an indented JSON block (each string capped at 512 characters, the block at 4,096, with a marker naming any argument cut off); and a compact footer: the exact tool id and, for a machine step, the requesting state as a quoted literal. The full model-facing tool description MUST NOT be rendered verbatim. A redaction hook lets the integrating developer mask sensitive argument fields before they leave the server; it receives a copy of the arguments, and if it throws, the block is replaced by `[redaction failed]`, never the arguments. On a multi-server facade the title, the purpose line and the footer name the box (R46), and the redaction hook receives the qualified name.

R17. On retry, an approved request executes the tool call and delivers `TOOL_RESULT` (or `TOOL_ERROR` if the underlying call fails) to the rehydrated machine. A declined request delivers `TOOL_DENIED` with the decline reason if provided (client-supplied text, neutralized and capped at 500 characters). A request missing from `inputResponses` is treated as declined. The workflow then continues; denial is not an automatic abort.

R18. Exceeding the round-trip cap is a `terminal` error; a retry after blob expiry is a `blob_verification` error. Both are structured (R25) and name their cause. The round-trip error says the workflow stopped unfinished, without reaching its final state, and its hint says the calls the machine had not made were not made: tell the user the task is incomplete, or finish it by issuing the remaining gated calls together with `toolCalls` (one round trip), leaving out the ones listed as already done (R15b), or with `call_tool` (D30). A blob minted before the cap was lowered fails the same way on resume, with the same list, and nothing from it runs.

### 6.5 Suspension blob (`requestState`)

R19. The blob is versioned, authenticated, and encrypted (AEAD, e.g. AES-256-GCM with an HKDF-derived key). Encryption is required, not optional, because machine context may contain data returned by read-only tool calls that would otherwise never transit to the client in code mode.

R20. Blob payload fields:

| Field                 | Purpose                                                                                                                                                                                                                                                                                                                             |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `v`                   | Blob schema version; unknown versions are rejected with a `blob_verification` error                                                                                                                                                                                                                                                 |
| `libv` / `xstatev`    | Library and XState versions that produced the snapshot                                                                                                                                                                                                                                                                              |
| `kind`                | `machine` (minted by `execute_machine`), `call` (minted by `call_tool`), `upstream_input` (minted by `call_tool` for a wrapped server's own question, R64) or `signin` (a sign-in suspension, R56); a blob opened by a tool other than the one that minted it is rejected (R36, R56)                                                |
| `codeHash`            | Binding hash (S4): SHA-256 of the original `code` for `machine` blobs, of the canonical `{ kind: "call", name, args }` request for `call` blobs (R36), of the original request for `signin` blobs (R56); the retried call must match                                                                                                |
| `serverIdentity`      | Identity of the wrapped server the blob was minted against (R30, R60), or of the whole server set on a multi-server facade (R41); the resuming facade must match                                                                                                                                                                    |
| `snapshot`            | `getPersistedSnapshot()` output of the machine actor (`null` for `call` blobs and for `signin` blobs not minted by `execute_machine`)                                                                                                                                                                                               |
| `pending`             | Map of inputRequest key → gated tool call (name, args, requesting state) awaiting a verdict; exactly one entry keyed `call` for `call` blobs (R35.3); a `signin` blob's deferred approvals (R56)                                                                                                                                    |
| `audit`               | Per-call approval audit trail accumulated in earlier segments (§8); `[]` for `call` blobs                                                                                                                                                                                                                                           |
| `prompts`             | `machine` blobs only: present, `'batched'`, only when the suspension was one batched approval prompt over two or more pending calls (R15); absent means one elicitation per pending call. Any other value, fewer than two pending calls, or the field on a `call` or `upstream_input` blob, is malformed                            |
| `trip`                | Round-trip counter for R18 (always 1 for `call` blobs; a sign-in round trip does not advance it, R57)                                                                                                                                                                                                                               |
| `nonce`, `iat`, `exp` | Replay scoping and expiry; default TTL 15 min for `machine` blobs (`blob.ttlMs`), 5 min for `call` blobs (`blob.callTtlMs`, R38), both configurable; a `signin` blob expires with its sign-in flow (R56)                                                                                                                            |
| `signin`              | `signin` blobs only (R56): the origin tool, the sealed flow state for each box, the held calls and the sign-in round-trip count; never a token                                                                                                                                                                                      |
| `upstreamInput`       | Calls that ran under the gate and wait on their own server's question (R64), keyed by call id: the recorded call, how it was authorized, the server's own `requestState` and the questions asked. Never part of `pending`. Exactly one entry keyed `call` for `upstream_input` blobs; optional on `machine` blobs; absent elsewhere |

R21. On resume the library MUST verify, in order: decrypt/authenticate, version compatibility, expiry, `kind` matches the opening tool, and the binding hash matches the re-sent `code` (`machine`) or the canonical request (`call`), plus `serverIdentity` (the R41 server-set string on a multi-server facade) — then, for `machine` blobs, re-evaluate the module, restore the actor from `snapshot` and inject verdict events; for `call` blobs, execute the single `pending` entry per R35.4. Any verification failure is a structured `blob_verification` error; the library never executes gated calls from an unverified blob. A `signin` blob is verified in a different order — decrypt/authenticate, version, `kind` and origin tool, binding hash and `serverIdentity`, then expiry — so only a blob that would otherwise open reports its expiry as phase `auth`; an expired `signin` blob opened at the wrong tool or with a different request stays `blob_verification` (R56). It then resumes per R57.

R22. Keys are provided by the integrating developer (env/config) and MUST be shared across instances of a horizontally scaled deployment. Key rotation with a grace window (accept N previous keys for decryption) is required.

R23. Serialized-and-compressed blob size SHOULD stay under 32 KB in typical flows; exceeding a configurable ceiling (default 128 KB) fails the suspension with an error advising the model to slim its context.

### 6.6 Validation and reactive self-healing

R24. Before first execution of any submitted code, the library transpiles (if TS) on the host, then runs a validation pass inside the sandbox: evaluate the module, confirm a default-exported v5 machine, reject banned patterns (R5, R7), count state nodes against the R12 cap, and round-trip a serializability probe (R6). Validation shares the segment budget; it is not a separate round trip.

R25. Every failure — transpile, validation, runtime exception, cap exceeded, blob verification, upstream — returns a normal tool result with `isError: true` and a structured body: `{ phase, message, diagnostics[], hint, logs[] }`, where `hint` is a one-line actionable fix (e.g. "Tool calls must use the toolCall action, not fromPromise; see discover_apis"). `upstream` is an `isError` result or transport failure from the wrapped tool, surfaced only by `call_tool` — inside a machine the same condition is a `TOOL_ERROR` event. Outcomes that are not failures — a human decline, a policy denial, a pending or declined upstream sign-in — are normal results: `TOOL_DENIED` in code mode, `{ status: "declined" | "denied_by_policy" }` from `call_tool` (D9), `{ status: "sign_in_required" | "sign_in_declined" }` (R55, R57). The design goal is that the model can rewrite and resucceed in one attempt without any human involvement. Phases: `transpile` (TS syntax); `validate` (contract violations, bad args, unknown tool, disallowed import, bad cursor, wrap-time configuration mistakes); `runtime` (uncaught sandbox error, stuck machine); `cap_exceeded` (any R12 cap); `blob_verification` (R21/R36 failures, replay); `protocol` (era/capability, introspection); `upstream` (wrapped tool failure, `call_tool` only); `auth` (an upstream sign-in could not complete: expired flow, authorization-server error, missing client registration, a sign-in host mismatch, invalid or insecure metadata; R52, R56, R57, R61 — every origin, machines included; it carries only library copy, the OAuth `error` code and a neutralized `error_description`); `terminal` (the workflow cannot continue: trip cap, blob over the R23 ceiling, key misconfiguration, no projection enabled).

R31. The sandbox captures all `console.log/info/warn/error/debug` output as structured entries `{ level, message, ts, segment }` and includes them in every completed result, every completed result and every `isError` result (a resumed segment's logs ride its own response), so the model can printf-debug its own machines. Capture is capped per the R12 table with an explicit truncation marker (drop middle, keep head and tail). Logs are execution telemetry only: never rendered into elicitation prompts (S6) and not persisted in the blob. Exception: the 2026-07-28 `input_required` result carries only `resultType`, `inputRequests` and `requestState` (D1), so the console output of the segment that suspends is not delivered.

R26. There is no compile-only or lint-only tool in v1. Validation always runs as the front of `execute_machine`, keeping the **code-mode** surface at two tools and the loop reactive.

### 6.7 Statelessness

R27. The library holds no cross-request state with two exceptions: the optional replay cache of R38 and, for sources given by URL, the token store of R59. A horizontally scaled deployment supplies both as shared stores. Per-instance state that holds no workflow state is also allowed: a box's locked or unlocked state and its lazily introspected catalog (R54), R55's pending fallback flow, and the loopback listener of R53.2 (phase 1b). Their outcomes reach other instances only through a shared token store: an instance where a box is still locked re-reads the store before acting on any request that names it, a resume included (R54). All resume information still rides in `requestState`, and every resume verifies and continues from it alone. All configuration is process-static. Compatibility target: plain round-robin load balancing per the 2026-07-28 transport model, including the `Mcp-Method`/`Mcp-Name` routing headers emitted by the host SDK.

R28. Down-negotiation. A client on a pre-2026-07-28 revision (no MRTR) can use every read-only path: `discover_apis`, `search_tools` (and `search_<alias>` on a multi-server facade), `describe_tool`, `auto`-policy `call_tool` calls, and machines whose calls are all `auto`. The moment a gated call would suspend, `execute_machine` and `call_tool` fail fast with a `protocol` error naming the required revision. Opt-in: `WrapOptions.compat.legacyElicitation` serves suspensions to legacy clients through the SDK's server→client `elicitation/create` shim (D6). The shim's re-invocation carries the same `requestState` echo and `inputResponses` as an MRTR retry, so R21 and S2–S4 are unchanged. It works only on held connections (stdio); per-request legacy HTTP has no server→client channel and fails cleanly. A client that did not declare the `elicitation` capability still gets Projection's structured fail-fast error at suspend time, not the SDK's unstructured one. Fail-fast is the default. A sign-in suspension (R55) is the exception to fail-fast. A legacy client without the opt-in, or one without the `elicitation` capability, gets the normal `sign_in_required` result instead of a `protocol` error, because the user can complete the sign-in out of band. Under the opt-in, the shim serves sign-in in its form shape.

### 6.8 Catalog projection

The catalog projection is the second way to drive the wrapped server: three tools in a lazy-catalog shape (search → describe → call). The search/describe half mirrors deferred tool loading as in Anthropic's tool-search feature and Goose; the polymorphic `call_tool` is Projection's addition, forced by R1 — the wrapped tools must never be passed through as callable tools themselves. Direct listing (R1, D28) lists a small catalog's tools by name, but each listed tool is a mediated alias of `call_tool`, not the server's tool. It exists for two reasons code mode does not serve well: a single action should not cost a 25-line machine, and a server with hundreds of tools cannot be described inline by `discover_apis` without flooding the context. It is deliberately not a second product: it shares the introspected catalog, the policy engine (R14), the elicitation copy (R16), the redaction hook, the blob sealer (R19–R23), the MRTR adapter and the legacy compat path (R28). Only the sandbox, the machine host and typegen's bridge are bypassed.

R32. The catalog projection consists of three tools: `search_tools`, `describe_tool`, `call_tool`. It is on by default and can be disabled per facade (`WrapOptions.projections.catalog: false`, R1); disabling it leaves code mode unchanged (and vice versa). On a multi-server facade it is those three plus one `search_<alias>` per box (R43). Direct listing (R1) is part of the catalog projection: when it lists the tools (by default, `projections.direct: 'auto'`, a catalog whose estimated definitions fit `directBudgetTokens`), a single-server facade serves the mediated tools plus `describe_tool` and `call_tool`, and not `search_tools`: there is nothing left to search. `describe_tool` then serves a listed tool's output schema, and `call_tool` stays the entry point that takes a catalog name. With `projections.direct: false` the catalog projection is exactly the three tools.

R33. `search_tools({ query?: string, cursor?: string })` returns a page of tools in catalog order, or ranked when `query` is given. Each entry is `{ name, purpose, posture, destructive }`: `purpose` is the first sentence of the full description, neutralized and capped per S5; `posture` is one of three normative strings — `runs immediately`, `asks for approval`, `blocked by policy` — the same words every surface uses (the `discover_apis` overview and `search_tools` show them verbatim in brackets; the `.d.ts` doc comments lead each tool with them in sentence case); `destructive: boolean` comes from `destructiveHint`. Matching: the query is lowercased, NFC-normalized and split on any run of characters that are not a letter, combining mark or digit; duplicate tokens are dropped; tokens shorter than two characters are dropped, and if none survives the whole trimmed query is the single token (so `a b` matches the literal `a b`; a whitespace-only query matches nothing; an absent or empty query lists every tool). A tool matches when any token is a case-insensitive substring of its name, annotation title or full description. Matches are ranked by the sum over tokens of `w × (2 × [in the name] + [in the title or description])`, where a token's weight `w = 1 + ln(N / df)` counts how many of the `N` tools searched it occurs in at all (`df`), so a word every tool has weighs 1 and a rarer word more; the two terms are independent, so a token in both name and description scores 3w. Ties rank first the tool whose name the query's name-hit tokens cover the larger share of, then keep catalog order (D10, D22). `query` is truncated at 200 characters and is never interpreted as a regex. **Call signatures** (D32): the first three hits of a query (`SIGNATURE_HITS`; ranks 1–3 of the whole ranking, so only on its first page, and never on a listing without a query) also carry `signature: { text, complete, callable }`, unless their posture is `blocked by policy`. `text` is one line built from the R34-sanitized input schema's top level: `{owner: string, repo: string, state?: "open"|"closed" = "open"}` — required arguments first, then optional ones marked `?`, each with its JSON Schema type (`T[]` for arrays, `A|B` for type lists and small `anyOf`/`oneOf`, a literal union for `enum`/`const` of at most 12 members, longer cut with `…`), and `= <default>` for a default R34 keeps. A property name that is not a plain identifier is JSON-quoted after neutralization; one over 64 characters is left out, never cut; a type word outside the JSON Schema vocabulary prints as `any`. Optional arguments stop at 480 characters (`…N more`), required ones at 960. `complete` is false when anything is left out (a nested object or array-of-objects shape, a constrained map, a `$ref`, a cut enum or argument, a truncated schema); `callable` is false when a required argument has a nested or unrendered shape or is left out, or the top level is not a plain object (a cut enum still lists valid values, so it does not count). The text rendering puts it on its own line under the entry, indented: `  args: <text>`, followed by `(describe_tool has the full schema)` when not complete, or `(call describe_tool first: a required argument is nested or not shown)` when not callable. **Argument glosses** (D33): a hit with a signature also carries `glosses: [{ name, text }]` for its required arguments whose sanitized description says what the name does not — none for an `enum` or `const` argument (the signature lists its values), for one without a description, or for one whose description is made only of filler words (articles, prepositions, `name`, `number`, `id`, `value`, `new`, `required`, …) and words of the tool's or its arguments' names, matched as prefixes. Each gloss is the description on one line (invisible characters stripped, whitespace collapsed, control and bidi characters neutralized), cut at a word to 120 characters (`MAX_GLOSS_CHARS`); a tool's glosses stop at 240 characters, and an argument whose name is over 64 characters gets none. The text rendering puts them on one more indented line under the args line, each JSON-quoted: `  where connectionId: "Use the id …"; sha: "…"`; a gloss already shown on the page (same argument, same text) is left out of a later hit's line. **Shared arguments** (D34): a required argument that at least half of a server's (box's) deduplicated tools, and at least three, require under the same name with the same rendered type — flat (no nested shape, no cut enum, not `any`) and with no default R34 keeps — is shared; a server has at most four, most shared first, their `{…}` capped at 240 characters, and each carries the gloss (above) that at least half of the tools sharing it give it. A page leads, above its `Tools …` header, with one line per box whose shared arguments it shows: `Shared args (most <alias> tools take them): {connectionId: string, database: string}, where connectionId: "…"` (`most tools here` on a single-server facade), for every box with a tool on a listing page and every box with a signed hit on a query page, and not for a box listed directly (R43). A signed hit's text then names a required shared argument without its type (`args: {connectionId, database, newName: string}`) when its type matches the line's and it has no default; `structuredContent` keeps the whole signature and glosses, and a hit's `where` line leaves out a gloss the shared line shows. The result carries `structuredContent: { tools: [{ name, purpose, posture, destructive, signature?, glosses? }], nextCursor?, total }` plus a text rendering. Pages hold 50 tools for a listing and 15 for a query (fixed transport bounds, independent of the R37 threshold; D32) and carry `nextCursor` when more remain; `cursor` is opaque and bound to the `query` that produced it, so a malformed cursor or one issued for a different `query` is a `validate`-phase error. The result tells the model that a tool shown with its args can go straight to `call_tool`, and to call `describe_tool` first for any other tool (a page without a signature keeps the plain `describe_tool` pointer). On a multi-server facade `search_tools` searches every box and each `search_<alias>` one box, both with these semantics plus R43's alias tokens, `box` field and tool-bound cursors.

R34. `describe_tool({ name, types? })` returns everything the model needs to call one tool: the neutralized and capped description, `inputSchema` and `outputSchema` as JSON Schema, annotations, and the resolved policy posture. With `types: true` it also returns the generated TypeScript types for that tool — the `<Pascal>Input` / `<Pascal>Output` aliases and the `tools.<name>` member signature exactly as they appear in `projection://types/tools.d.ts`, so a machine authored from `describe_tool` output type-checks against the full resource. Types are opt-in because the JSON Schema already carries the shape and the types roughly double the payload; `call_tool` callers never need them. The schemas are an S5 surface in their own right: beyond `description`, a server controls free text in `title`, nested `description`, `examples`, `default`, `$comment`, `x-*`, `enum` and `pattern`. They MUST therefore pass through a key allowlist — `type, properties, required, items, prefixItems, enum, const, anyOf, oneOf, allOf, not, $ref, $defs, additionalProperties, description, title, format, minimum, maximum, minLength, maxLength, pattern, default` — `default` only as a scalar (a finite number, a boolean, `null`, or a string of at most 64 characters with no control, bidi or invisible character; anything else is dropped, never cut), restated after the input schema as one `Defaults the server applies when an argument is omitted: …` line and as an `@default` tag in the generated types, because an omitted argument silently takes it (D29) — with every string value neutralized (control and bidi characters) and the rendered schema capped at 16 KB per tool with an explicit truncation marker; `annotations.title` is neutralized the same way. An unknown name is a `validate`-phase error whose hint names the closest declared tools — the name's tokens ranked as a `search_tools` query (D10), kept only when a token matched the tool's name, at most three, neutralized and capped per S5 — and then points at `search_tools`. The result also carries `destructive` and `schemaTruncated` (true when either schema was reduced by the size, depth or name caps). On a multi-server facade `name` is qualified, the types are the `tools.<alias>.<name>` slice (R45), the did-you-mean hint is scoped to the named box when there is one (R40), and the hint names the search tools the facade serves (R43).

R35. `call_tool({ name, args })` runs one wrapped tool under the same gate as a machine step (on a multi-server facade `name` and every result's `tool` are qualified everywhere below, R40):

1. **Validate** the name against the catalog (an unknown name fails as in R34, with the same did-you-mean hint) and `args` structurally against `inputSchema`. `args` MUST be a JSON object (not an array or `null`) serializing to at most `maxInputBytes` (R12); larger is `cap_exceeded`. Structural checks — required properties present; top-level property types match; top-level primitive values are members of the property's `enum`; no unknown top-level properties when the schema forbids them — use own-property semantics (`__proto__` and `constructor` as keys are ordinary data). Failures are `validate`-phase errors whose hint names the offending property and restates the tool's call signature, with the property's gloss when it has one (R33, D32, D33: `"<tool>" takes args: {…}, where <property>: "…". Fix argument "<property>" and try again.`; a hint gloss is cut at 240 characters), so a call made without `describe_tool` costs at most one retry; the same hint serves a machine's `toolCall` (R15a). Full JSON Schema validation is out of scope; the wrapped server remains the authority, and its rejection surfaces as an `upstream` error (R25).
2. **Decide policy** (R14). `auto` executes immediately. `deny` returns a normal (non-error) result `{ status: "denied_by_policy", tool, reason }`. `ask` suspends.
3. **Suspend** with one MRTR elicitation built by the R16 copy builder and a sealed `call` blob (R36) whose single `pending` entry is `{ id: "call", name, args, stateName: "call_tool" }` — the blob shape is unchanged. The copy builder takes an `origin` option (`"machine" | "direct"`) that selects the footer, kept plain for a non-technical approver: `Tool: <id>` for direct calls, `Tool: <id> · workflow step "<state>"` for machines. R28 and `compat.legacyElicitation` apply unchanged; an `auto`-policy `call_tool` always works on a legacy connection.
4. **Resume**: the retry re-sends `{ name, args }` and the echoed `requestState`. After R21 verification (and the R38 replay check when a cache is configured) an accepted elicitation executes the call with the args recorded in the blob's `pending` entry (S2 — never the retry's own args); a declined, missing or non-elicitation response returns a normal result `{ status: "declined", tool, reason? }` (R17 semantics). Policy is decided on the retried name before the blob is opened: a tool that is now `deny` returns `denied_by_policy` without opening the blob or spending a replay nonce (D9).
5. **Result shape**: success is `{ status: "ok", tool, output }` where `output` follows the `TOOL_RESULT.result` rule (structuredContent when present, else the single text block, else `null` / the raw content array) — except that `output` keeps a JSON text block as the string it is, where a machine receives it parsed (a single text block holding JSON for an object or an array becomes `TOOL_RESULT.result` parsed, with the text on `TOOL_RESULT.text`; authoring contract rule 8, D29); the text rendering prints a string output raw and a structured one as indented JSON, in which a top-level string of three or more lines is replaced by a `[string: N lines, shown as text below]` marker and printed after the JSON as its own lines, under a `"<key>" (string, N lines):` header and indented like any untrusted block (at most five such fields; D29, D30); an upstream failure is an `isError` result with phase `upstream`, whose hint restates the tool's call signature (D32), since the server enforces what the shallow R35.1 check does not, followed by the glosses (R33, D33; cut at 240 characters) of the arguments the call sent, optional ones included. If the output's JSON exceeds `maxResultBytes` (R12) the result is still `ok` — the call ran, and an error would read as "retry" — with `output` replaced by the first 1,000 characters of that JSON, `truncated: true` and `outputBytes`. A decline is an outcome, not an error: the tool description MUST tell the model not to retry an identical call without the user asking for it, and the declined result carries the R15b copy. The description also says where arguments come from — a search hit's args or `describe_tool` — and points to `execute_machine` for multi-step work. Facade tool annotations: `search_tools` and `describe_tool` carry `readOnlyHint: true`; `call_tool` carries none, so hosts that gate on annotations never auto-run it. A directly listed mediated tool (`projections.direct`, `<alias>__<tool>`) advertises Projection's own annotations, never the server's: `readOnlyHint: true` only when Projection runs the call without asking (`auto`) and the server marks it read-only and not destructive, so never under an `ask` or `deny` override; `destructiveHint: true` when the server marks the tool destructive, as a warning (`false` is never advertised); no annotation `title`, `idempotentHint` or `openWorldHint` (the listed tool's own `title` is the neutralized one).
6. **Result notes** (D29). An `ok` result may carry `notes`: at most three one-line remarks the facade derives from the result, the call's arguments and the tool's input schema, printed under the head line (between it and the blank line that opens the body, where the server's text cannot reach) and returned in `structuredContent.notes`. Three conservative detectors, each declining on an ambiguous shape: (a) **count** — the result (or its JSON text) is an object with exactly one top-level array and an integer total-like sibling (`total`, `count`, `total_count`, `<array>Count`, …, or the same keys in a `meta`/`pagination` object) larger than the array: `Partial result: "<array>" holds N of M (per "<key>"). …`; (b) **full page** — the schema has a page-size argument (`limit`, `perPage`/`per_page`, `pageSize`/`page_size`, `max_results`/`maxResults`, `first`), and the main array's length equals the effective page size (the argument sent, else its kept default, R34), with no total-like key saying the array is complete: `Page full: N items, exactly … so more may exist. …`, naming the schema's next-page argument (`page`, `cursor`, `offset`, `after`, …) when it has one; (c) **server note** — text blocks beside `structuredContent` of at most 500 characters together that are not JSON, do not contain the structured value's JSON and do not merely restate its values in prose: `Note from the server, beside its structured result: "<text>"`. Every server-controlled fragment (key names, the note text) is stripped of invisible characters, whitespace-collapsed, neutralized, capped and JSON-quoted (S5); the note text is redacted like the result (S1). A machine receives the same notes on `TOOL_RESULT.notes`, and a completed `execute_machine` restates its segment's notes (at most 10, each prefixed with the quoted tool name) in a text block after the output and in `structuredContent.notes`, because the output is model-authored and may drop them.

R36. `call` blobs reuse the R20 payload with `kind: "call"`, `snapshot: null`, `trip: 1`, `audit: []`, all other fields as for `machine` blobs, and `codeHash` computed over the canonical JSON of `{ kind: "call", name, args }` — domain-separated from code hashes by construction, not by the accident that a machine module can never equal a JSON literal. The binding hash is a coherence check, not the approval binding: S2 is carried by `pending` alone. It exists so a result is only ever returned to the request the approver saw (a stale approved blob cannot be attached to an unrelated `call_tool` request). Canonical JSON: only object keys are sorted, by UTF-16 code unit order; array order is significant; canonicalization runs on the _parsed_ request, so `1`/`1.0`, `-0`/`0`, escaped vs literal characters and duplicate keys (last wins) canonicalize identically; no Unicode normalization is applied (NFC and NFD differ — fail closed); absent `args` ⇒ `{}`; the canonicalizer MUST throw `validate` on non-JSON values (`undefined`, functions, bigint, non-finite numbers) rather than drop them. `openBlob` already hashes a caller-supplied string, so the adapter passes the canonical text where `execute_machine` passes `code`. Verification MUST reject — as `blob_verification` errors, before anything executes — a payload without `kind` (malformed), a blob whose `kind` does not match the tool opening it, a `call` blob whose binding hash does not match the retried request, and a `call` blob whose `pending` has anything other than exactly one entry keyed `call`. `BLOB_SCHEMA_VERSION` stays 1, on multi-server facades too (R40: the qualified `name` is what is hashed).

R37. Catalog scale. When the catalog projection is enabled and the catalog exceeds a size threshold (default 40 tools; `WrapOptions.catalogInlineThreshold`), `discover_apis` omits the per-tool list from its inline overview and prints the tool count plus a pointer to `search_tools` / `describe_tool`; the `.d.ts` resource stays complete. Otherwise the inline overview — already one line per tool — is unchanged. The threshold is a prompt-budget bound and the R33 page size is a transport bound; the two knobs are independent. On a multi-server facade the threshold counts tools across all boxes, and the pointer names the search tools the facade serves (R43, R45).

R38. Replay cache (optional). `WrapOptions.replayCache?: { seen(nonce: string, exp: number): Promise<boolean> }`. When configured, the adapter consults it after R21 verification and before executing any gated call, for both blob kinds; a nonce already seen is a `blob_verification` error. No default implementation ships — an in-memory one would silently break horizontal scaling (G4). The nonce is recorded on first sight, whatever the verdict, so an approval blob is single-use. `call` blobs use the shorter TTL of R20 because an approved `call` blob has no forward step and is a standing capability until `exp` (D4, D9). An `upstream_input` blob (R64) keeps the `exp` of the blob it continues (the approving `call` blob, or the previous question's blob) and is never given a fresh TTL, so an approval and all its forwarded questions live at most one `callTtlMs`. A configured cache is recommended wherever forwarding (R64) is on: without one, a captured question blob can re-issue the already-authorized call until it expires.

### 6.9 Multiple servers

One facade can front several wrapped servers. Each server is a **tool box** under an alias the integrating developer chooses, every tool is addressed by its qualified name `<alias>.<name>`, and the catalog projection gains one search tool per box. Both projections, the policy engine, the approval path and the blob sealer are shared across boxes exactly as §6.8 shares them between projections; there is no new suspension or approval mechanism. "Multi-server facade" in this document means any facade built by `wrapMcpServers`, whatever its number of sources. Rationale: DECISIONS D16 (and D17 for R49, which applies to single-server facades too).

R39. **Entry point.** `wrapMcpServers(sources: Record<string, McpServer | Client | UpstreamSpec | ServerSourceConfig>, options: WrapServersOptions): Promise<MultiProjectionFacade>` builds a multi-server facade (`UpstreamSpec`: a source given by URL, R51).

- `ServerSourceConfig = { source: McpServer | Client | UpstreamSpec; description?: string; approvals?: ApprovalsMode; upstreamElicitation?: 'forward' | 'refuse'; optional?: boolean }` (`approvals`: R49; `upstreamElicitation`: R64; `optional`: R47). A source value is a `ServerSourceConfig` when it is a plain object with an own `source` property and neither a `callTool` nor a `connect` function; any other key in it is a `validate` error, so a misspelt setting is never silently dropped. The same source object (an identical `McpServer` or `Client`) under two aliases is a `validate` error.
- `WrapServersOptions extends WrapOptions { catalog?: { globalSearch?: boolean } }` (R43). `wrapMcpServer` takes `WrapOptions` and does not accept `catalog`.
- `MultiProjectionFacade` has every `ProjectionFacade` member, with these differences: `catalog: ToolCatalog` is the alias-keyed catalog of the wrapped boxes; `skipped: readonly { alias: string; error: StructuredError }[]` lists the optional sources that were skipped (R47); `searchTools(args, alias?)` runs `search_<alias>` when `alias` is given and `search_tools` otherwise, returning an R25 `validate` error result when that tool is not served (an unknown or skipped alias, or `globalSearch: false`); `describeTool` and `callTool` take qualified names; `close()` closes every connection Projection opened.
- Aliases match `^[a-z][a-z0-9]{0,23}$`: short enough that `search_<alias>` stays within host tool-name limits, dot-free so a qualified name splits unambiguously (R40), underscore-free so `search_<alias>` and the R45 type names map back to exactly one alias. Reserved: `default` (`DEFAULT_SERVER_ALIAS`, the single-server alias) and every suffix Projection registers after `search_` — `tools` today, and the suffix of any fixed `search_*` tool added later. The grammar admits JS/TS reserved words (`delete`, `new`); R45 emits object types so they are valid aliases. A facade takes 1–16 sources (R48).
- Every configuration mistake in R39, R42 and R49 is a `validate` `ProjectionError` raised at wrap time, before any source is connected.
- Aliases are the only server names any model-visible or approval surface shows. Every surface that names the server identity on a single-server facade — the search and `describe_tool` headers, the `discover_apis` overview header and the `tools.d.ts` resource description, the `.d.ts`, bridge and overview headers, the workflow prompts — names the alias instead (the sorted alias list where the surface spans the facade). A server's self-reported `serverInfo.name` and `instructions` are S5-untrusted and never stand in for its alias; the server identity enters only the blob (R41).
- `description` is host-trusted text naming the box's purpose (R43, R44), still neutralized (control and bidi characters) and capped at 200 characters.
- `wrapMcpServer(source, options)` keeps today's behaviour: its outputs — goldens, blobs, copy — stay byte-identical. It is not reimplemented as a one-source `wrapMcpServers`, and a `wrapMcpServers` facade always uses qualified names, even with one source.

R40. **Qualified names.** On a multi-server facade every tool is named `<alias>.<name>`, split at the first dot; a server's own tool name may contain dots and stays inside its box (`fs.github.issue_write` is the `fs` box's tool `github.issue_write`). The qualified name is used on every model-facing and approval surface: search results, the `name` of `describe_tool` and `call_tool`, the `tool` field of `call_tool` results (R35) and of `execute_machine` audit entries (R2), generated types (R45), `toolCall` names in machines, approval copy (R46), blob `pending` entries and the R36 binding hash. Consequences: an approval for `fs.write_file` can never be replayed as `github.write_file`; two servers' same-named tools never collide; the S5 first-occurrence dedupe applies within each box. An unqualified name, or one whose alias or tool is unknown (a skipped box included, R47), is a `validate` error whose did-you-mean hint (R34, D10 addendum) shows qualified names. When the name's alias part is a wrapped box, the suggestions come from that box only; only an unqualified name or an unknown alias ranks across all boxes. The alias rides inside the recorded name, so the blob format does not change (R30): `BLOB_SCHEMA_VERSION` stays 1.

R41. **Identity and key domain** (amends R19, R21, R30). A multi-server facade's `serverIdentity` is `multi:` followed by `JSON.stringify` of its `[alias, identity]` pairs sorted by alias, where `identity` is the R30 per-server string (`${name}@${version}`, or `url:<canonical url>` for a source given by URL, R60) — e.g. `multi:[["fs","files@1.2.0"],["github","gh-server@0.9.1"]]`. JSON encoding makes the string injective whatever a server reports. Every blob the facade mints binds it, so a blob cannot resume on a facade with a different server set, alias mapping or server versions. A single-server identity is server-controlled and stays byte-identical, so the string format alone cannot separate the two facade kinds: a server may report a name that spells a multi-server identity. Multi-server facades therefore derive their per-blob keys in a separate HKDF domain — info string `@astral-mcp/projection/blob/v1/multi`; single-server facades keep `@astral-mcp/projection/blob/v1` — so a blob never crosses between the two facade kinds, under the same key and whatever the identity strings say; it fails authentication (`blob_verification`). The blob format is unchanged. Only wrapped boxes count: a skipped optional source (R47) is absent, so a blob minted while it was down does not resume on a facade where it is up, and vice versa — fail closed.

R42. **Policy** (amends R14). On a multi-server facade per-tool overrides live only in the facade-level `options.policy`, keyed by qualified names; sources carry none. An unqualified key, or one whose alias names no configured source, is a `validate` error (a typo must not silently drop a `deny`). Configured, not wrapped: a key for a skipped optional box (R47) is ignored, as is a key naming an unknown tool in a known box (as on a single-server facade). Policy is resolved per qualified tool, by R49's precedence, and frozen at wrap time; every other R14 rule — the override wins, fail-safe `ask`, re-evaluation on resume — applies per box unchanged.

R49. **Approvals mode** (amends R14). `approvals?: ApprovalsMode`, where `ApprovalsMode = 'every-write' | 'destructive-only'`, default `'every-write'` (today's behaviour), is settable on `WrapOptions` — applying to the whole facade, single- or multi-server — and on each `ServerSourceConfig`, where it applies to that box and takes precedence over the global value. Under `'destructive-only'` a tool runs without approval only when it is not read-only and its annotations explicitly declare `destructiveHint: false`; a missing `destructiveHint`, or any value other than an explicit `false`, still asks, matching the MCP default that a non-read-only tool is destructive. Read-only tools run immediately in either mode. Precedence, strongest first: the facade's per-tool `policy` override (a per-tool `ask` or `deny` always beats a relaxed mode, and a per-tool `auto` still auto-runs), then the per-source `approvals`, then the global `approvals`, then the annotation default (R14). The resolved decision is what every surface shows: the R33 postures, the `.d.ts` doc comments and the overview flags. A malformed value — anything but the two strings — fails the wrap with a `validate` error. The mode is part of the resolved policy, so R14's resume rules apply to it unchanged. S5: the mode extends the trust Projection already places in `readOnlyHint` to `destructiveHint: false`, and a hostile server can mislabel a damaging tool; integrators enable it per source, for servers they trust. Rationale: DECISIONS D17.

R43. **Tool boxes in the catalog projection** (amends R32–R35, R37). With the catalog projection on, a multi-server facade lists one `search_<alias>` per box, taking `{ query?, cursor? }` with R33 semantics scoped to that box; `search_tools`, searching every box at once; and one `describe_tool` and one `call_tool`, taking qualified names. That is N + 3 tools for N boxes, plus the two code-mode tools when code mode is on, when no box is listed directly (`projections.direct: false`, or no box fits the budget). `WrapServersOptions.catalog.globalSearch` (default `true`) turns `search_tools` off, leaving N + 2; the default is to be confirmed by the multi-server eval (§13).

- **Direct listing** (R1; default `projections.direct: 'auto'`, D28). Boxes are listed directly smallest first (by estimated definition tokens, ties by alias) while their running total fits `directBudgetTokens`; a listed box's tools appear as mediated `<alias>__<tool>` tools, and every other box keeps its `search_<alias>`. A listed box's `search_<alias>` is served only when its server sends `instructions`, so its overview stays readable; `search_tools` is served only while some box is not listed (and `globalSearch` is on). `describe_tool` and `call_tool` still take qualified names. The preamble and the shelf say which boxes are listed directly and how their tools are named (R44). `projections.direct: false` restores the N + 3 surface; `true` lists every box.

- **Global ranking.** `search_tools` uses the D10 tokens and scores, matched against each tool's own name, title and description (never its alias), with one exception: a query token equal to a wrapped box's alias is an **alias token** — it adds a name hit of the query's heaviest text token (2 × its weight, or 2 when there is none) to the score of every tool in that box and is not matched against any tool's name, title or description. Token weights count the tools searched across every box. A server cannot outrank another box's tools for that box's alias by writing the alias into its own text.
- **Results.** Both search tools return entries `{ name, box, purpose, posture, destructive }`, `name` qualified. Ties break by name coverage (R33), then sorted alias order, then catalog order. Cursors carry the issuing tool (`{ t, q, o }`) and are valid only at that tool; a cursor without `t`, or issued by another search tool, is a `validate` error. The first page of an empty-query `search_tools` leads with one line of per-box tool counts, so one large box does not hide the others.
- **Box description.** `search_<alias>` carries `readOnlyHint: true`. Its tool description is `Search the <alias> toolbox.`, then the box's `description` unquoted, else the first sentence of the server's `instructions` quoted and attributed (`<alias> — "…" (server's words)`, neutralized and capped per S5), else nothing; then the box's tool count.
- **Box overview** (progressive disclosure). The first page of an empty-query `search_<alias>` leads with the server's full `instructions`, neutralized and capped at 8 KB with an explicit truncation marker (`structuredContent.overview`). The text rendering shows it as an indented block, as `describe_tool` renders a description, under the header `Guidance from the <alias> box (the server's own words; it applies to <alias> tools only):`; the tool-list header follows unindented. A box whose server sends no `instructions` has no overview.
- **Search-tool naming.** Every piece of library copy that names `search_tools` — the unknown-name hint (R34, R40), the `describe_tool` and `call_tool` argument descriptions, the R37 pointer, the preamble (R29, R44) — names the search tools the facade actually serves: `search_tools` and the `search_<alias>` tools, or only the latter when `globalSearch` is `false`.
- **Locked boxes** (R54) change what these surfaces show, never which tools are served: a locked box's `search_<alias>` suspends for sign-in, its description is fixed at wrap time, and its tools are absent from `search_tools` until it unlocks.

R44. **Instructions** (amends R29). On a multi-server facade the `instructions` are Projection's multi-server preamble — the R29 routing rule, naming the served search tools (R43), and that a box's own guidance is its overview — followed by the **shelf**. With both projections on, the multi-server routing rule also sends a short chain that looks something up and then acts on it to `call_tool`, one step at a time, reading each result before the next, and keeps `execute_machine` for work that loops or branches over results, takes many steps, or is a workflow worth saving; the multi-server `execute_machine` and `call_tool` descriptions carry the same rule (`execute_machine`'s only when `call_tool` is also served). The shelf header states the qualified-name rule (tools are `<alias>.<name>`), so a `codeModePreamble` override cannot drop it. Under direct listing (R43) the preamble names the boxes listed directly and their `<alias>__<tool>` naming, and the shelf header says so too: every box listed, or a box marked "listed directly" with the others searched by their `search_<alias>`, each listed box's line then carrying `, listed directly`. Below it, one line per box: its alias, then its `description` unquoted, else the first sentence of the server's `instructions` quoted and attributed (`<alias> — "…" (server's words)`, neutralized and capped per S5), and its tool count; no posture counts. A box with shared arguments (R33, D34), not listed directly, gets one more indented line under it, names and types only: `  shared args: {connectionId: string, database: string}`. A locked box's line reads `<alias> — sign-in required`, followed by its `description` when one is given, with no tool count (R54). The wrapped servers' full instructions are not concatenated into the system prompt; the box overview (R43, R45) is where they are read. `codeModePreamble` replaces Projection's preamble wholesale; the shelf, header included, is kept, like a single server's forwarded instructions under R29. Single-server facades keep R29 as is.

R45. **Code mode** (amends R3, R4, R7, R30, R37). Typegen emits one object-type property per box — `export declare const tools: { fs: { read_file: …; "github.delete_repo": … }; … }` — never TypeScript namespaces, so reserved words are valid aliases; tool names that are not identifiers use today's quoted form. Type aliases are `<alias>_<Pascal>Input` / `<alias>_<Pascal>Output` (`fs_ReadFileInput`): an alias contains no `_` (R39), so the names are unique across boxes and independent of which other boxes are wrapped. `describe_tool({ types: true })` returns the `tools.<alias>.<name>` slice under the header `// Member of tools.<alias>:`. Machines call `toolCall('<alias>.<name>', args)`, the bridge's `tools.<alias>.<name>` members bind the same qualified name, and the host routes by alias. `discover_apis`' inline overview groups the tool list per box; above the R37 threshold, counted across all boxes, it prints per-box counts and points at the served search tools (R43). It also links each box overview as a resource (`projection://boxes/<alias>/overview.md`, R3), so a box's guidance is reachable with the catalog projection off. The authoring contract gains one rule: on a multi-server facade, tool names are qualified. The examples (`happy-path`, `denial-fallback`, the authoring-contract samples) use qualified names from the facade's first box in sorted alias order — its own tools where it has a suitable read-only and gated one, else generic names marked as sample names. One machine may span boxes; each gated call is approved separately, and R15 batching applies unchanged (parallel gated calls to different boxes share one round trip, one elicitation each). A locked box (R54) is absent from the types, the bridge and the overview until it unlocks; a `toolCall` to it gets a `TOOL_ERROR` event naming the box's search tool (phase 1b: it suspends for sign-in).

R46. **Approval copy** (amends R16). On a multi-server facade the title reads `Approve (<alias>): <action>`, with the ⚠ prefix and warning line for destructive tools as today, the action still derived from that box's catalog entry. The purpose line is always rendered: `What <alias> says it does: "…"`, or `What <alias> says it does: (no description)` when the server gives none. The footer reads `Tool: <alias>.<name>`, or `Tool: <alias> › "<name>"` when the bare tool name contains a dot (so `fs`'s tool `github.delete_repo` never reads as the `github` box's), with the workflow-step suffix as today (` · workflow step "<state>"`). The alias is the host's, never the server's self-reported name (S6).

R47. **Availability.** Wrapping is fail-closed: if any source cannot be connected or introspected, `wrapMcpServers` fails and every connection Projection opened is closed (caller-owned `Client`s stay open; the introspector settles every source before cleaning up). `WrapOptions.introspectTimeoutMs` (default 30 000 ms) bounds each source's connect and introspection, on single- and multi-server facades alike; a source that has not finished in time fails the wrap. A source marked `optional: true` is skipped instead of failing the wrap, on error or timeout: it is reported on `facade.skipped` and is absent from the shelf, the search tools, `describe_tool` / `call_tool`, the types and the identity (R41). At least one source must succeed, or the wrap fails. An `UpstreamSpec` source (R51) that answers 401 has not failed: it comes up locked (R54), whatever `optional` says, and a locked box counts as a success here. A skipped source is not retried; picking it up means wrapping again. Known limitation: behind a load balancer (R27) instances may disagree on which optional boxes were skipped, so their identities and tool lists differ and blobs fail with `blob_verification` across them; integrators running several instances should not mark sources optional. A server that fails mid-workflow surfaces exactly as today — a `TOOL_ERROR` event in a machine, an `upstream`-phase error from `call_tool` — except that a 401 from an `UpstreamSpec` box re-locks it and suspends for sign-in (R58). A box's `tools/list_changed` refreshes nothing: the catalog, types, shelf and identity stay as wrapped.

R48. **Limits.** At most 16 sources per facade. Per-server introspection bounds are unchanged (2000 tools, 100 pages; D12), and a facade holds at most 4000 tools in total, checked after introspection. Exceeding a per-server bound fails that source (skipped if `optional`); exceeding the total fails the wrap whatever `optional` says. Both are `protocol` errors, like today's introspection limits. The R12 caps are per facade, not per box: the auto-run cap counts calls to every box in a segment. Known cost: the bridge covers every box, so a facade near 4000 tools loads a large bridge into every `execute_machine` sandbox. Lazy introspection when a locked box unlocks (R54) is bounded the same way.

### 6.10 Just-in-time upstream sign-in

A wrapper starts with no upstream credential anywhere: none in an MCP client's configuration file, an environment variable, argv or code. Projection connects to a remote server by its URL. The first time a model touches a server that requires authorization, Projection suspends the request over MRTR (the same way it suspends for an approval), asks the user to sign in and then continues. Sign-in uses the same suspension machinery (blob sealer, MRTR adapter, legacy compat path) and adds a separate kind of request. Pre-built `McpServer`s and `Client`s keep today's behaviour, with the integrator owning the transport and its auth. This section serves a single principal (R62). Rationale: DECISIONS D19.

In this section, **box** means a source of a multi-server facade, or the whole of a single-server facade. A single-server facade's box has no alias, so copy that would name the alias names the source URL's host instead.

**Phases.** §6.10 ships in two phases.

- **Phase 1** (the GitHub milestone): an `UpstreamSpec` with a configured `oauth.clientId` (R51, R52); the keyring token store with its in-memory fallback (R59); the device flow with the hold-and-poll retry (R53, R57); URL and form elicitation, and the `sign_in_required` fallback backed by a per-instance pending flow that the next call redeems (R55); locked boxes for `search_<alias>`, `describe_tool` and `call_tool`, and for `search_tools`, `describe_tool` and `call_tool` on a single-server facade (R54); re-lock on 401 (R58); `signOut` without revocation (R59); and the live GitHub smoke (§13).
- **Phase 1b**: authorization code + PKCE with the loopback listener (R53, R61); DCR and CIMD (R52); `insufficient_scope` step-up (R58); RFC 7009 revocation on `signOut` (R59); the `discover_apis` suspension (R54); and machine-held sign-in (R54, R56, R57).

Text marked _(phase 1b)_ belongs to phase 1b; everything else is phase 1.

R50. **No upstream credential in configuration.** Projection never needs an upstream credential in its configuration to wrap a server it connects to by URL (R51). Such a wrap succeeds with no token anywhere. The first request that needs an authorization the user has not granted suspends for sign-in (R55) instead of failing. Projection reads no upstream credential from environment variables, argv or MCP client configuration for these sources. The only upstream credentials it holds at rest are the ones the user granted through sign-in, and they live in the token store (R59). A client secret (R52) is registration configuration, not a user credential, and is discouraged. A credential carried in the source URL's query string (an API key as a query parameter) is out of scope: Projection treats the URL as configuration, not as a secret, and integrators should not put credentials in it (R51).

R51. **Upstream sources by URL** (amends R39). `UpstreamSpec = { url: string | URL; oauth?: UpstreamOAuthOptions }` is accepted wherever a source is: as the `source` of `wrapMcpServer`, as a source value of `wrapMcpServers`, and as a `ServerSourceConfig.source`. A source value is an `UpstreamSpec` when it is a plain object with an own `url` property, no own `source` property, and neither a `callTool` nor a `connect` function. Any key other than `url` and `oauth`, and any unknown key inside `oauth`, is a `validate` error (R39's rule). For such a source Projection builds the transport and installs its own auth on it: an SDK `AuthProvider` whose `token()` reads the token store and whose `onUnauthorized()` runs the SDK's `auth()` over Projection's `OAuthClientProvider`, a fresh delegate per auth run (R58). It owns the resulting `Client` and closes it in `close()`. Streamable HTTP is the only transport Projection builds.

- **URL rules.** The URL is parsed with the WHATWG URL parser; a URL longer than 2048 characters is a `validate` error, as is an endpoint override that long. `https:` is required, except that `http:` is allowed on the loopback hosts `127.0.0.1`, `[::1]` and `localhost`. Userinfo (credentials in the URL) and a fragment are `validate` errors. The **canonical URL** lowercases the scheme and host, drops a default port, writes an empty path as `/`, keeps the query, and percent-encodes every `@` in the path and query as `%40`, so a canonical URL never contains `@` (R60). Two sources with equal canonical URLs are a `validate` error, like one source object under two aliases (R39). The query is part of the resource's identity and is kept in the canonical URL; a credential in it is out of scope (R50).
- **OAuth options.** `UpstreamOAuthOptions = { clientId?, clientSecret?, clientMetadataUrl?, scopes?: string[], signInHosts?: string[], authorizationEndpoint?, tokenEndpoint?, deviceAuthorizationEndpoint? }` holds registration (R52), flow overrides (R53) and the sign-in host allowlist (R61). Every endpoint and `clientMetadataUrl` must be `https:`, otherwise it is a `validate` error. The loopback exemption applies only when the source URL is itself a loopback URL. Each `signInHosts` entry is a bare lowercase ASCII hostname (punycode for internationalized names; no scheme, port, path, wildcard or IP address literal), otherwise a `validate` error. Until phase 1b, `clientMetadataUrl` and `authorizationEndpoint` are `validate` errors, since nothing would use them.
- **Pre-built sources are unchanged.** A pre-built `McpServer` or `Client` keeps today's behaviour: Projection installs nothing on its transport, and a 401 from it surfaces as it does today (a failed wrap, a `TOOL_ERROR` event, an `upstream` error). A facade built only from such sources keeps every output byte-identical: goldens, blobs, copy and identity.

R52. **Client registration: bring your own.** Projection ships no OAuth client registration for any provider and recommends none. It resolves its client identity with an authorization server in the order the SDK's `auth()` uses:

1. `oauth.clientId`, with `oauth.clientSecret` when one is given. This is a client the integrator registered beforehand.
2. _(phase 1b)_ `oauth.clientMetadataUrl`, a Client ID Metadata Document that the integrator hosts. It is used when the authorization server advertises `client_id_metadata_document_supported`.
3. _(phase 1b)_ Dynamic client registration (RFC 7591), when the server's metadata has a `registration_endpoint`. This is the path that needs no configuration. The MCP authorization specification deprecates DCR in favour of CIMD; Projection supports it for servers that offer nothing else.

_(phase 1b)_ The DCR request registers `application_type: "native"` and the grant types of the flow R53 chooses, plus `refresh_token`. For the authorization-code flow it also registers the loopback redirect URI, whose port may vary per RFC 8252 §7.3. A DCR result is a credential (it may carry a secret the server issued), so it lives in the token store (R59), keyed by issuer, canonical resource and principal, and a restart does not register again.

A client secret is discouraged: the device flow (R53) needs none, and integrators should prefer it. When none of the options applies, the request ends directly in an `auth`-phase error (R25), with no elicitation round trip. The error names the box, says what the server lacks (a registration endpoint, CIMD support) and names the option to set: `oauth.clientId` for that box, on a registration with the device flow enabled. It never contains a secret.

R53. **Flows.**

1. **Device authorization grant (RFC 8628)** is used whenever the authorization server supports it: its metadata has a `device_authorization_endpoint`, and `grant_types_supported`, when present, lists `urn:ietf:params:oauth:grant-type:device_code`. Setting `oauth.deviceAuthorizationEndpoint` also selects it. In phase 1 it is the only flow: an authorization server without it is an `auth` error that names `oauth.deviceAuthorizationEndpoint` and the integrator-owned `Client` path. The device flow needs no redirect listener and no client secret, and it is **stateless across retries**: the device code, polling interval and expiry are sealed in the sign-in blob (R56), so any instance can hold and poll it (R57).
   - **Redemption.** SDK 2.3.1 has no device-flow client. Projection sends the device authorization request itself, then redeems the device code through the SDK's token-request path (`fetchToken`), with `prepareTokenRequest` returning the device-code grant (R58's provider rules). Client authentication, resource indicators, issuer stamping and the token endpoint's TLS check therefore stay the SDK's.
   - **Client authentication.** When `oauth.clientSecret` is set, the device authorization request authenticates the client too, with the method the SDK's `selectClientAuthMethod` picks. Projection applies that method itself, because the SDK does not export `applyClientAuthentication`.
   - **Scopes.** The SDK does not export its scope selection, so the device flow replicates it: `oauth.scopes` when set, else the protected resource metadata's `scopes_supported`, else none. Integrators should set `oauth.scopes` explicitly; the GitHub recipe and the live smoke do (§13).
2. _(phase 1b)_ **Authorization code with PKCE** is used otherwise. Only S256 is accepted; an authorization server whose `code_challenge_methods_supported` omits `S256` is an `auth` error. The redirect URI is `http://127.0.0.1:<ephemeral port>/callback` (listener rules in R61). The `state` parameter is a sealed value: AEAD as for blobs, under its own HKDF info string `@astral-mcp/projection/signin-state/v1`, so a state value never opens as a blob and a blob never opens as a state value. It carries the PKCE verifier, the box, the canonical resource, the recorded issuer (for the SDK's callback-leg issuer binding), a nonce and an expiry. Whichever process receives the callback can therefore complete the exchange from the state alone. It redeems the code through the SDK's `auth()` with `authorizationCode` and `iss` (the SDK checks RFC 9207), stores the tokens (R59), and answers the browser with a static page that reflects nothing from the request.
3. **Resource indicators.** Every authorization, device-authorization and token request carries RFC 8707 `resource`: the protected resource metadata's `resource`, validated against the source URL by the SDK (`selectResourceURL`), as the MCP authorization specification requires. Not every authorization server honours it (GitHub's does not), so audience binding does not rest on it; Projection enforces it on its own side (R61).
4. **Overrides** serve servers with incomplete metadata. `oauth.authorizationEndpoint` _(phase 1b)_, `oauth.tokenEndpoint` and `oauth.deviceAuthorizationEndpoint` replace the discovered values of the same name. `oauth.scopes` replaces the SDK's scope selection (the metadata's `scopes_supported`, or a step-up challenge). Overrides are host-trusted configuration and still subject to R51's `https:` rule; an overridden endpoint is exempt from R61's sign-in host rule.
5. **No hosted redirects.** Hosted (non-loopback) redirect URIs are out of scope (§12.4). The loopback flow works only when the browser runs on the same machine as Projection, and Projection cannot detect when it does not. A hosted deployment whose authorization server has no device flow uses an integrator-owned `Client`.

R54. **Locked boxes and lazy introspection** (amends R3, R29, R33, R37, R43–R45, R47, R48). At wrap time an `UpstreamSpec` source connects with whatever token the store holds for it (R59). The box comes up **locked**, and the wrap does not fail, in either of two cases: connecting or introspecting answers HTTP 401, or the SDK raises `UnauthorizedError` because a stored token neither works nor refreshes. A locked box is wrapped, not skipped:

- `optional` does not apply to it.
- It counts in the identity (R41, R60).
- Its alias is valid in policy keys (R42), and its overrides apply once its tools are known.

While a box is locked:

- **Shelf and box search tool.** The shelf (R44) lists the box as `<alias> — sign-in required`, followed by the host's `description` when one is given, and shows no tool count. Its `search_<alias>` is still served, so the tool set does not change (R43).
- **Fixed search-tool description.** A tool's description cannot change without a `tools/list_changed`, so a box's `search_<alias>` description is fixed at wrap time. For a box that comes up locked it is `Search the <alias> toolbox.`, then the box description, then `May ask the user to sign in first.` in place of the tool count, and it stays that way after the box unlocks. A box that comes up unlocked keeps its R43 description, tool count included, if it later re-locks (R58).
- **Absent tools.** The box's tools are absent from search results, the `.d.ts` and the bridge, the `discover_apis` overview and the R37 count. The box has no overview resource.
- **Global search.** `search_tools` does not suspend. Its first page leads with a line that names the locked boxes and the search tool that signs in to each.
- **`discover_apis`** does not suspend in phase 1. It names the locked boxes and the search tool that signs in to each. Until phase 1b, an `UpstreamSpec` source on a facade with the catalog projection off is a `validate` error at wrap time, because nothing would reach a locked box.
- **What suspends for sign-in** (R55):
  - `search_<alias>`.
  - `describe_tool` or `call_tool` with a name qualified by the box's alias.
  - _(phase 1b)_ A machine `toolCall('<alias>.<name>')`. The host holds the call without validating it, because it has no catalog for the box yet, and the machine waits as it would for an approval. Typed bridge members exist only for unlocked boxes; `toolCall` is the path that reaches a locked box. In phase 1 the machine receives a `TOOL_ERROR` event instead, whose message says the box needs sign-in and names its search tool, so the model can sign in through `search_<alias>` and run the workflow again.
  - _(phase 1b)_ `discover_apis`, when the catalog projection is off, because nothing else reaches a locked box. It then suspends for every locked box at once, one elicitation each (R15 batching). With the catalog projection on, `discover_apis` does not suspend.
- **Policy before sign-in.** A configured `deny` for the qualified name wins without sign-in: `call_tool` returns `{ status: "denied_by_policy" }` and a machine `toolCall` receives `TOOL_DENIED`, and nothing suspends. Only a configured override can decide this while the box is locked; annotations are not yet known.
- **Token store first.** Any request that names a box locked on this instance, a resume included, first re-reads the token store. If it finds a token (stored by another instance or process, or by a redeemed fallback flow, R55), the instance introspects the box as described below, before any policy decision, and the request proceeds without asking. This is how a resume that lands on an instance where the box is still locked continues: R35.4's policy check on the retried name needs the box's catalog.

On the retry after a successful sign-in, the instance introspects the box. Introspection is lazy and runs once per instance, bounded by `introspectTimeoutMs` (R47) and by the R48 per-server and facade limits. If a limit is exceeded, the box stays locked, the request fails with the `protocol` error R48 names, and the token is kept. The original request then proceeds as if the box had been unlocked when it arrived:

- a search runs;
- `describe_tool` describes;
- `call_tool` validates and applies policy;
- _(phase 1b)_ a held machine call is validated against the new catalog and dispatched through policy.

Projection's own tool set never changes when a box unlocks. No `tools/list_changed`, `resources/list_changed` or `resources/updated` notification is sent: the 2026-07-28 wire is stateless, and the facade holds no subscription state. The shelf and the `.d.ts`, bridge and overview resources reflect the unlocked box the next time they are read; tool descriptions do not change. A connection or introspection failure that is not an auth failure still fails closed (R47). That includes lazy introspection: the request fails with a `protocol` error and the box stays locked.

**Single-server facades.** A single-server facade over an `UpstreamSpec` is one box. While it is locked:

- `search_tools`, `describe_tool` and `call_tool` suspend for sign-in. A machine `toolCall` gets phase 1's `TOOL_ERROR` event, naming `search_tools` _(phase 1b: it suspends)_. `discover_apis` returns an overview with no tools that says the server needs sign-in and names `search_tools` _(phase 1b: it always suspends, because the box is all it describes)_.
- The forwarded server instructions (R29) are absent until the box unlocks.
- The preamble adds one sentence saying that the server asks the user to sign in on first use.

R55. **The sign-in request.** A sign-in suspends over MRTR as `input_required`, with one `inputRequests` entry per locked box that the request needs. Entries are keyed `signin:<alias>`, or `signin` on a single-server facade. Each entry takes the most capable shape the client declared (on 2026-07-28, the client capabilities sent with the request):

1. **URL mode**, when the client declares the `elicitation.url` capability; the SDK refuses a URL-mode request to any other client. The entry is the embedded request `{ method: "elicitation/create", params: { mode: "url", message, elicitationId, url } }`:
   - `url` is the device response's `verification_uri_complete`, else its `verification_uri`, or _(phase 1b)_ the authorization URL.
   - `elicitationId` is random per sign-in flow and stays the same across pending re-suspensions of that flow.
   - `message` reads `Sign in to <alias> (<resource host>)`, then `You'll be sent to <issuer host>`. `<resource host>` is the source URL's host; `<issuer host>` is the hostname of the validated authorization-server `issuer` (R61). On a single-server facade the first line reads `Sign in to <resource host>`. For the device flow the message adds `Code: <user code>` (always, since a client may open `verification_uri` rather than the complete URI) and the code's lifetime in minutes.
   - The alias is host-controlled, and both hosts come from validated URLs. The user code must match RFC 8628's recommended character set (letters, digits and `-`, at most 32 characters); any other code is an `auth` error. The message contains no server-authored prose (S6).
   - `accept` means "check now"; `decline` and `cancel` mean the user declined.
   - Projection never sends `notifications/elicitation/complete`. The 2026-07-28 revision removed it, and the client learns the outcome by retrying.
2. **Form mode**, for a client that declares only form elicitation. The form's message carries the same lines, with the link as inert text, and the form has a single required boolean `signedIn`, labelled "I've signed in". The legacy shim (`compat.legacyElicitation`, R28) always uses this shape, whatever the client declares: the shim re-invokes the tool as soon as the client answers, and a 2025-era URL-mode `accept` means "opened", not "done".
3. **No elicitation**, for a client without the `elicitation` capability, or a legacy client without the R28 opt-in. The result is normal (not `isError`): `{ status: "sign_in_required", box, url, userCode?, expiresAt }`. `box` is absent on a single-server facade, and `expiresAt` is ISO 8601. The text tells the model to show the link (and the code) to the user, not to open the link itself, and to call again once the user says they have signed in. From `execute_machine` _(phase 1b)_ it also says that the workflow did not complete and must be run again after sign-in.

   **Pending fallback flow.** With no retry envelope to carry the flow, the instance keeps it in memory: at most one pending fallback flow per box per instance, so another request for that box on that instance gets the same link and code rather than a new flow. Nothing polls in the background. The next request on that instance that needs the box redeems the flow: it re-reads the token store, then holds and polls as R57 describes. Tokens unlock the box and the request proceeds; a flow still pending returns `sign_in_required` again with the same link and code; an expired flow is dropped, and the request starts a new one. _(phase 1b)_ For the authorization-code flow the instance keeps its loopback listener up until the callback arrives or the TTL ends. A pending fallback flow never leaves its instance: behind a load balancer, the next call may reach another instance, which finds the token only through a shared token store (R27) and otherwise starts its own flow.

Sign-in copy is not approval copy: it has no `Approve` title and never names a tool or its arguments. Signing in never implies approval.

R56. **Sign-in blobs** (amends R20, R21, R36). The `requestState` of a sign-in suspension is a blob of a new kind, `kind: "signin"`, under the R19–R23 envelope: AEAD, versioned, and subject to the R23 size ceiling. `BLOB_SCHEMA_VERSION` stays 1, as it did when R36 added `call`. Strict `libv` rejection (Q3) already keeps older libraries from opening it.

Why a new kind, not a pending entry of the existing kinds: `pending` is the S2 approval map, and an entry that an `accept` must never execute does not belong in it. A separate kind keeps every approval path (the machine host's `applyVerdicts`, `call_tool`'s exactly-one-`call` rule) unaware of sign-in, and it means a sign-in blob can never be opened as an approval.

The payload is the R20 fields plus `signin: { origin, boxes, held, trips }`:

- `origin` is the tool that minted the blob: `call_tool`, `describe_tool`, `search_tools` (single-server), `search_<alias>`, or _(phase 1b)_ `execute_machine` or `discover_apis`. For a `signin` blob, R21's kind check becomes "opens only at its `origin` tool".
- `codeHash` binds the original request, so the retried request must be the one that suspended. It is the SHA-256 of:
  - the R36 canonical request, for `call_tool`;
  - the canonical JSON of `{ kind: "describe", name, types }` or `{ kind: "search", tool, query, cursor }`, for `describe_tool` and the search tools;
  - _(phase 1b)_ `code`, for `execute_machine`, and the canonical JSON of `{ kind: "discover" }`, for `discover_apis`.
- `serverIdentity` is set as for every blob (R60).
- _(phase 1b)_ For the `execute_machine` origin, `snapshot` is the machine snapshot. `pending` holds the suspending segment's gated calls awaiting approval; they are raised as approvals once the sign-in resolves, and the sign-in does not answer them. `audit` and `trip` are as for `machine` blobs.
- For every other origin, `snapshot` is `null`, `pending` and `audit` are empty, and `trip` is 1.
- `boxes` holds, per alias, the flow state:
  - the flow (`device`, or _(phase 1b)_ `authorization_code`);
  - for the device flow: the device code, the interval and the expiry;
  - the expiry and the `elicitationId`;
  - the recorded issuer and the canonical resource.

  It never holds a token.

- `held` holds the `call_tool` request, or _(phase 1b)_ the machine calls (callId, qualified name, args, requesting state), that need the box. They are dispatched once the box unlocks.
- `trips` counts sign-in round trips. It is separate from `trip`, which a sign-in round trip does not advance (R57).

`exp` is the device code's `expires_in`, or 10 minutes for the authorization-code flow, and the earliest of those across the blob's boxes. Verification of a `signin` blob runs in this order: decrypt/authenticate, version, `kind` and `origin` tool, binding hash and `serverIdentity`, then expiry. An expired `signin` blob that passes every earlier check reports phase `auth` ("the sign-in expired; call again"), not `blob_verification`, because the blob authenticated, opened at its own tool and binds this request. Every other failure stays `blob_verification`, so an expired `signin` blob opened at the wrong tool, or with a different request, is a `blob_verification` error. The R38 replay cache applies to `signin` blobs, so each is single-use.

R57. **Retry outcomes.** A retry carrying a `signin` blob first passes verification in R56's order and the R38 replay check. Each box in the blob then resolves to one of these states, checked in this order:

- **Declined**: the user declined or cancelled, the response is missing (R17), or the authorization server answered `access_denied`.
- **Signed in**: the token store holds a token for the box. The store is re-read before any poll, so a token that another instance or process stored is found without polling.
- **Signed in or pending, from the device flow.** Otherwise the retry **holds** the request and polls the token endpoint at the flow's interval for at most 25 seconds, polling every pending box of the request concurrently:
  - A `slow_down` adds 5 seconds to the box's interval, per RFC 8628, for the rest of the flow.
  - Tokens mean the box is signed in, and they are stored (R59).
  - `authorization_pending` and `slow_down` keep the box polling; still pending when the hold ends, the box is pending.
  - `expired_token`, or the flow's expiry passing during the hold, is an `auth` error.
  - The hold ends as soon as every box has resolved. It runs before any execution segment starts, so it does not spend the R12 segment wall clock.
- _(phase 1b)_ **Pending**, from the authorization-code flow, while no token has been stored yet.

Then, for the request as a whole:

- **All signed in.** The boxes unlock (R54) and the original request continues. A `call_tool` to a gated tool then suspends for approval with a fresh `call` blob. _(phase 1b)_ A machine's held gated calls join its `pending` approvals in a fresh `machine` blob. Signing in never implies approval, not even for a call approved before a 401 re-locked its box (R58).
- **Any box pending.** Nothing is dispatched. The request re-suspends with a fresh `signin` blob for the pending boxes: same flows (with any adjusted interval), same `elicitationId`s, same `exp`, `trips + 1`, `trip` unchanged, and declined boxes recorded. Sign-in round trips do not count against the R12/R18 round-trip cap; the loop is bounded by the flow's expiry, after which the retry is an `auth` error. A pending loop never turns into R55's `sign_in_required` result for a client that can elicit. In particular, _(phase 1b)_ a `signin` blob from `execute_machine` whose `audit` records an executed gated call keeps re-suspending until `exp`, because running the workflow again would repeat those writes.
- **Declined.** `call_tool`, `describe_tool`, the search tools and _(phase 1b)_ `discover_apis` return a normal result `{ status: "sign_in_declined", box }`; the copy tells the model not to call again unless the user asks. _(phase 1b)_ In a machine, every held call for the declined box receives `TOOL_DENIED` with the reason `sign-in declined`, and the workflow continues (R17).
- **Failure.** The request ends with an `isError` result with phase `auth`, for every origin, machines included: the model cannot fix the cause by rewriting, only report it. Causes include an authorization-server error, an expired flow, missing registration (R52), a sign-in host mismatch (R61), and invalid or insecure metadata. The message and hint name the box and the cause, in library copy. From the authorization server they carry only the OAuth `error` code, when it matches `^[a-z_]+$` (otherwise it is dropped), and its `error_description`, neutralized per S5 and capped at 500 characters. They never carry SDK error text or token-store library errors.

R58. **Re-lock on 401.** An unlocked `UpstreamSpec` box re-locks when a call answers 401 (the SDK raises `UnauthorizedError`) after the provider's own refresh attempt has failed, for example because the token expired or was revoked. Two processes sharing one store entry is normal (two MCP clients that each run the wrapper, for example), so the store, not the instance, decides:

- **Re-read before refresh.** The provider's `tokens()` reads the store on every call, so a refresh starts from the latest stored record, and a token another process has already refreshed is used rather than refreshed again.
- **Re-read before re-lock.** If the store now holds a different token from the one that failed, the call is sent once more with it instead of re-locking.
- **Compare-and-delete.** Re-lock deletes the stored record only if it still equals the record whose token failed (read, compare, delete), so a token another process has just stored survives. The box's catalog is dropped; the next unlock introspects again.

The request then suspends for sign-in as R54 describes instead of failing. Inside a machine this is _(phase 1b)_ a sign-in suspension of the held call; in phase 1 it is a `TOOL_ERROR` event naming the box's search tool (R54).

A 401 means the upstream did not run the call, so sending it again after sign-in, or with a token another process stored, is not a duplicate. A gated call is still approved again (R57).

**Provider rules.** Projection's `OAuthClientProvider` never starts an interactive flow inside the transport:

- It always sets a loopback `redirectUrl`, even when no listener runs, and its `redirectToAuthorization` only records that sign-in is needed. The transport then raises `UnauthorizedError`.
- `prepareTokenRequest` returns a grant only inside a per-redemption delegate, created for one device-code redemption and discarded after it. The provider holds no shared mutable flow state, so concurrent redemptions for different boxes or requests cannot cross.
- Four errors mean sign-in is needed: `UnauthorizedError`, `InsufficientScopeError`, an error carrying Projection's own auth-seam marker, and the `SdkHttpError` with code `ClientHttpAuthentication` that the transport raises when a request still answers 401 after `onUnauthorized` ran (the same condition one step later). Every other error is not an auth failure and surfaces as it would for any upstream, with every credential the connection presented redacted from its text (R59).
- The provider reaches the transport as an SDK `AuthProvider`, not as the `OAuthClientProvider` itself: `token()` reads the store per request, and `onUnauthorized()` runs the SDK's `auth()` over a fresh `OAuthClientProvider` delegate created for that one run, so the console capture below covers exactly the run and compare-and-delete deletes exactly what the delegate presented. Refreshes are single-flight per stored record within a process: concurrent 401s on one record share one refresh, and a 401 whose token is no longer the stored one is retried with the stored token instead of refreshing.
- Every request goes through Projection's fetch: a bearer token is sent only to the canonical resource (origin and path), a redirect from it to any other URL is refused rather than followed, and for a source that is not loopback nothing is sent over `http:` — the token endpoint included (the SDK's own check admits a loopback `http:` token endpoint for any source).
- The transport is built with `onInsufficientScope: 'throw'` and the SDK's default `redirectPolicy`, never `'follow'`.
- The SDK's `console.warn` output during auth calls is captured and dropped, so nothing it prints reaches stderr or the client's logs. On first auth use (importing the library changes nothing), `console.warn` becomes an accessor property: assigning it stores the function as usual, and reading it returns that function, except inside an auth run's async context, where it returns a wrapper that drops `[mcp-sdk]` warnings. A logger that replaces `console.warn` at any time, mid-run included, is therefore still filtered inside auth runs and untouched outside them.
- An auth run (a refresh, its discovery included) is bounded by 30 seconds and ends when its facade closes. A run that times out or is aborted is `refresh_failed`, with the record kept; the single-flight refresh it held clears, so the next call starts a fresh one. Every request of a run, and every request of the connection, is sent with `redirect: 'manual'`: redirects are never followed by the underlying fetch.

**Insufficient scope.** A 403 with `error="insufficient_scope"` raises `InsufficientScopeError`. In phase 1 it is an `auth` error (a `TOOL_ERROR` event in a machine) saying that the granted scopes do not cover the call and naming `oauth.scopes`. _(phase 1b)_ The box re-locks as above, and the new sign-in requests the union of the granted and the challenged scopes (the SDK's `computeScopeUnion`); with `oauth.scopes` set, the phase 1 error applies.

R59. **Token residence** (amends R27, S1). Tokens live only in a `TokenStore`:

```ts
interface TokenStore {
  get(key: string): Promise<string | undefined>;
  set(key: string, value: string): Promise<void>;
  delete(key: string, expected?: string): Promise<boolean>;
}
```

Keys and values are opaque strings; a store never parses them and returns values byte for byte. `delete` with `expected` is the compare-and-delete of R58: it deletes only when the stored value is still exactly `expected`, and reports whether it deleted. Values are Projection's own serialization. A key is `<kind>:<JSON array>`, so a store can route or label by the kind before the first `:`. Projection derives two kinds of key:

- `tokens:[canonical resource URL, client id, principal]`, a token set. Its value is ASCII JSON `{ access_token, refresh_token?, expires_at?, scope?, issuer }`; an `id_token` is never stored;
- _(phase 1b)_ `registration:[issuer, canonical resource, principal]`, a DCR registration.

**Default store.** The OS credential store, through the native keyring library `@napi-rs/keyring`: prebuilt binaries for the macOS Keychain, the Linux Secret Service and the Windows Credential Manager, with no subprocess, so a secret never appears in argv and no size limit applies.

- **Optional dependency.** `@napi-rs/keyring` is an optional dependency of `@astral-mcp/projection`, loaded with a dynamic import on first use.
- **Fallback.** If the module is not installed or fails to load, or the platform store is unavailable or locked, Projection uses an in-memory store for the rest of the process, with a one-time stderr warning that sign-in will not survive a restart. Each store operation is guarded by a 5-second timeout; a timeout counts as unavailable.
- **Entries.** Service `@astral-mcp/projection`; account the lowercase hex SHA-256 of the store key, so neither URLs nor query strings appear in the store's metadata; where the library supports a label, a human-readable one that names only the resource host.
- **Verified writes.** Every write is read back and compared; a mismatch counts as a store failure. Operations on one entry are serialized within the process; a write that timed out but lands later is reconciled (rewritten with the newer value, or compare-and-deleted), and after the fallback a rotated value is still written to an entry the process has seen, best effort (reconciled the same way if it lands late, so it cannot bring back a signed-out token), and `delete` still deletes the OS entry, or fails when the entry may be there: the process has seen the key in the OS store, some OS-store operation has succeeded in this process, or the module failed to load (rather than not being installed). On a machine with no working OS store, `delete` returns the in-memory result. Compare-and-delete is read, compare, delete: not atomic across processes, which R58 accepts.
- **No library text.** Errors from the library are never logged or surfaced verbatim: a store failure is reported in fixed library copy.
- **Threat model.** The OS store protects tokens against other OS users and against theft of the disk. It does not protect them from code running as the same user: any process of that user (an npm `postinstall` script, another MCP server) can read the item. That is true of every OS-store approach.

There is no plaintext file store, and no file store encrypted under the blob key.

**Pluggable store.** `WrapOptions.tokenStore` replaces the default. It is how a hosted single-tenant deployment keeps tokens, and a horizontally scaled one needs a shared store: the second shared state R27 admits, after the R38 replay cache.

**Refresh and sign-out.** Refresh is automatic: a record whose `expires_at` has passed is refreshed before it is sent, and a 401 refreshes as R58 describes, starting from the latest stored record, and rotated refresh tokens are saved. `facade.signOut(alias?)` deletes the stored tokens of one `UpstreamSpec` box, or of every such box when called without an alias, and re-locks them on this instance. Other instances re-lock on their next 401 (R58). _(phase 1b)_ Before deleting, `signOut` makes a best-effort RFC 7009 revocation when the authorization server advertises a `revocation_endpoint`; a failed revocation does not fail `signOut`. DCR registrations are kept. An unknown alias, or the alias of a box not built from an `UpstreamSpec`, is a `validate` error.

**Where credentials never go** (normative). Access tokens, refresh tokens and client secrets never enter the sandbox, a blob, a log, stderr, an error message or any model-visible surface. Device codes and PKCE verifiers exist only sealed, inside a blob or a `state` value (R53, R56), and in the memory of the instance that holds a pending fallback flow (R55); they never appear in clear on any surface.

**Redaction of echoes.** A server given by URL sees the access token on every request and may echo it. Everything such a source returns (wrap and call errors, results, the catalog, its instructions) is scrubbed of every credential the connection presented or was given, replaced by `[redacted]`. Redaction is exact matching against accidental echoes: the raw value and its URL-, form-, JSON-, base64- and base64url-encoded spellings, also once invisible characters are stripped (box surfaces strip them). It is not a defence against a hostile server, which can always re-encode a token it was sent. Only string values are scrubbed, never property names or JSON syntax; a value that cannot be checked or rebuilt (or whose property name carries a credential) fails closed with an error. A secret shorter than 8 characters is never substring-redacted, since that would corrupt the server's text without hiding anything; it is still never logged. Redaction runs before any truncation, so a cut cannot leave a credential's prefix.

R60. **Identity** (amends R30, R41). For a source given by URL, the R30/R41 per-server identity is `url:<canonical url>` (R51). It is host-controlled and the same whether the box is locked or unlocked, so a sign-in blob minted while the box was locked verifies after it unlocks. The server's reported `name@version` is not part of it. On a single-server facade over an `UpstreamSpec`, this string is the `serverIdentity`, under the single-server key domain. On a multi-server facade it is the box's entry in the R41 pairs, for example `["github","url:https://api.githubcopilot.com/mcp/"]`.

A canonical URL never contains `@` (R51), while R30's `name@version` always does. No server can therefore report an identity equal to a URL identity.

Trade-off, recorded in D19: an upgrade of the server behind the URL no longer invalidates in-flight blobs. A resumed call is validated against the catalog the instance holds when the call is resumed.

R61. **Security requirements.**

- **Discovery.** Endpoints come from one of two places. The first is the source's RFC 9728 protected resource metadata (from the `WWW-Authenticate` `resource_metadata` parameter, or the well-known URL), followed by RFC 8414 / OpenID authorization server metadata. On that path the SDK's checks apply: the metadata's `resource` must match the source URL (`checkResourceAllowed`), the issuer must echo (RFC 8414 §3.3), the callback's `iss` is checked (RFC 9207), and stored tokens and registrations are bound to their issuer. Projection never sets `skipIssuerMetadataValidation`. The second place is the explicit host overrides of R53.
- **HTTPS.** Every authorization-server endpoint, every `verification_uri` and every authorization URL must be `https:`. The only exemption is loopback, and only when the source itself is loopback.
- **Sign-in host.** A hostile server can name a legitimate but unrelated identity provider, so where the user is sent is checked against the issuer. `authorization_endpoint`, `device_authorization_endpoint`, `verification_uri` and `verification_uri_complete` must share the host of the validated authorization-server `issuer`; otherwise the sign-in fails with an `auth` error. Two exceptions: an endpoint the integrator set as an explicit override (R53), and a host listed in `oauth.signInHosts`. GitHub passes, since its issuer, endpoints and verification URI are all on `github.com`. Google's device flow, for example, sends the user to hosts other than its issuer's and needs them in `oauth.signInHosts`. The sign-in message names both the resource host and the issuer host (R55).
- **Displayed URL.** The URL the elicitation shows, and the client opens, is the validated URL. Every host shown is a hostname as the parser gives it: ASCII, punycode for internationalized names.
- _(phase 1b)_ **Loopback listener.**
  - It binds `127.0.0.1` only (never `0.0.0.0` or `::`), on an ephemeral port.
  - It runs only while an authorization-code sign-in is pending, and closes after one callback that ends the flow, when the TTL ends, or when `close()` is called; `close()` stops every listener.
  - It accepts only `GET /callback` with a `state` that opens (R53) and has not been seen before. That check uses the R38 cache when one is configured, and a per-process set otherwise.
  - A callback with a valid `state` and an `error` parameter ends the flow (declined for `access_denied`, an `auth` error otherwise) and closes the listener.
  - The token exchange sends exactly the `redirect_uri` of the authorization request.
  - Its response page reflects nothing from the request and is sent with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
- **Single-use flow state.** The `state` value, the PKCE verifier and the device code are sealed and single-use, and R38 applies to sign-in blobs.
- **No token passthrough** (MCP authorization specification). When Projection is served over HTTP with its own authorization, a credential the MCP client presents to Projection is never forwarded upstream. Upstream requests carry only tokens that Projection obtained for that resource.
- **Audience binding.** RFC 8707 `resource` asks the authorization server to bind a token to its resource, but servers may ignore it (GitHub's does), so Projection enforces the binding on its own side: endpoints come only from metadata whose `resource` matches the source URL, and a token is stored under, and sent only to, the canonical resource it was obtained for. A hostile upstream cannot make Projection send a token to a different resource: not to another box's server, not to a protected resource metadata document that names another resource (the SDK rejects it), and not across a redirect. Projection does not follow an upstream redirect to another origin with a token attached.
- **Threat-model note.** In R55's no-elicitation fallback, the link and the user code pass through the model, and the risks run in two directions:
  - **Phishing.** A model steered by injected content could show the user a different link or code instead of Projection's, for example a device code for an attacker's client. Projection cannot stop that on a channel it does not control. The URL-mode and form shapes never pass the link through the model, and the fallback copy tells the model to relay the link verbatim.
  - **Fixation.** If the code leaks to an attacker who approves it first, Projection ends up signed in to the attacker's account: whoever approves a device code grants Projection their own account, never the user's. The user's later writes would then land in the attacker's account.

  The fixation risk is accepted for single-user phase 1. A leaked code is single-use, expires within minutes, must be approved before the user approves it, and gains the attacker no access to the user's account. The user also sees the outcome in the upstream's own interface, and `signOut` undoes it.

R62. **Scope: one principal.** The principal is the person running the wrapper, over local stdio or in a single-user HTTP deployment whose endpoint the integrator protects. Every request to the facade acts as that principal with the stored tokens; the principal component of every token-store key is the fixed string `local`. Blobs are not bound to a principal. Out of scope, and held in §12.4:

- per-user and multi-tenant principals, and principal-bound blobs;
- hosted (non-loopback) redirect URIs;
- secret references for static tokens;
- credentials carried in a source URL (R50).

An integrator-owned `Client` with its own transport auth remains the path for all of these.

### 6.11 Upstream questions

A wrapped server may ask its user something mid-call: confirm a choice, pick an account, or open a link to connect an account (MCP elicitation, form or URL mode). On 2026-07-28 it does so by answering `tools/call` with `input_required`. Rationale: DECISIONS D24 (and D7 for why only that era).

R63. **Upstream era** (G2). Every client Projection opens to a wrapped server negotiates the 2026-07-28 revision: an in-process `McpServer` is served over an in-memory pair through the SDK's connection-pinned entry (`serveStdio` with a supplied transport) and the client pins the revision; a server given by URL is probed (`versionNegotiation: 'auto'`) and falls back to the 2025 handshake when it speaks only that. Auto-fulfilment is always off, so an upstream `input_required` reaches Projection as data. The client declares the `elicitation` capability (form and URL) only for a box that forwards questions (R64), and only where the server negotiated 2026-07-28: a box given by URL that falls back to the 2025 era reconnects declaring nothing. A caller-provided `Client` keeps whatever its owner negotiated (D7). Blob identity is unaffected. An `input_required` that carries state and no question (MRTR's "call me again") is re-issued at once with that state, at most 8 times per call; past that the call fails. Known limitation: serving pins the caller's `McpServer` instance to the 2026-07-28 handlers, so after `close()` it can be wrapped again but not hand-connected to a 2025-era client.

R64. **Forwarding** (G1). `upstreamElicitation?: 'forward' | 'refuse'` on `WrapOptions` (for `wrapMcpServers`, the default of every box) and on `ServerSourceConfig` (per box, overriding it). Default `'refuse'`; any other value is a `validate` error at wrap time.

1. **Refuse.** No elicitation capability is declared, so the server's own SDK refuses the question; if a server asks anyway, Projection refuses it. `call_tool` returns an `upstream`-phase error saying the tool asked the user for input, with a hint that the arguments were not the problem and that a retry asks again; a machine gets a `TOOL_ERROR` with the same message. The same holds for sampling and roots, on every box.
2. **Gate first.** A question is forwarded only from a call that already ran under the gate: `auto`, or approved through its own `call` blob. Forwarding never runs a gated call (S2): an answer re-issues the recorded call, and nothing else.
3. **Suspension.** `call_tool` returns `input_required` with one elicitation per server question (at most 4), keyed `upstream-<n>`, and an `upstream_input` blob under the R19–R23 envelope: `codeHash` is the R36 canonical request, `pending` is empty, `upstreamInput` holds the recorded call, its authorization (`auto` or `approved`), the server's own `requestState` (at most 16 KB) and the questions; `snapshot: null`, `audit: []`; `trip` counts the round trips of the call (an approval, then each question), capped by R18; TTL is `blob.callTtlMs` from the call's first blob, carried forward and never extended (R38). In a machine, the call is held: the actor keeps waiting for its event, the segment suspends once nothing else can run, and the held call's questions join that suspension next to any approvals (R15), sealed in the machine blob's `upstreamInput`. At most 4 questions are held per suspension, across calls: a call that would exceed that, or whose question cannot be forwarded (8. below), gets its `TOOL_ERROR` at once. Two in-flight calls sharing an id are a `validate` error. A machine that reaches its final state while only held calls remain completes without asking; the held calls are audited as unfinished. `BLOB_SCHEMA_VERSION` stays 1; strict `libv` rejection keeps older libraries from opening either.
4. **Resume.** R21 verification, the R38 replay check, and the D9 rule run as for approvals: a tool now `deny` is not re-issued (`denied_by_policy` or `TOOL_DENIED`), and neither is a call that ran without approval (`auto`) and whose tool now asks (`call_tool`: a `blob_verification` error whose hint says to call again; a machine: `TOOL_DENIED`), so a new `ask` override is never bypassed by a blob minted before it. The recorded call is re-issued with the server's `requestState` and one answer per question: an accepted form carries only the fields of the form the human saw, each of its type; an accepted link carries no content; `decline` and `cancel` pass through; a missing answer, or one of another kind, is a `cancel`. The server may ask again (another round trip) or complete; its result is the call's result.
5. **Copy** (S5, S6). The first line is `Question from <alias> (not an approval)` (`Link from …` for URL mode; `the server` on a single-server facade); the copy names the tool as a quoted id, says the answer approves nothing, and quotes the server's message under `<alias> wrote:` with every line prefixed `│ `, invisible characters stripped, control and bidi characters neutralized, capped at 1,000 characters, lines hard-wrapped at 100 characters (each piece prefixed, so a client's soft wrap never shows an unprefixed line) and at most 16 lines. A form title, description or option label that mimics approval copy (a `⚠` anywhere; `Approve`, `Approved`, `Approval` or any `approv…` word, `Tool:` or `What … says it does` at the start after any leading `[k]`, numbering, glyphs or punctuation; or an approval form's own field text) is prefixed `The server's text: `. Every option is shown by a title: an untitled `oneOf`/`anyOf` option is titled with its value, and an `enum` with a member that mimics approval copy becomes titled options, so an option value is never shown unmarked; an untitled field whose name mimics approval copy (`Approve_delete_repo`) gets its name, marked, as its title; a string `default` that mimics approval copy is dropped. Field names of Projection's own approval forms (`approve_<n>` and `reason`, any case) are dropped. The requested schema is reduced to the elicitation primitives: at most 12 fields named as identifiers (never an approval form's field name); string (title, description, length bounds, the four formats, enum with labels kept only when every member survived, titled options, default), number and integer (bounds, default), boolean (default), and multi-select arrays of string options; every string neutralized and capped; everything else dropped, `required` filtered to surviving fields.
6. **Links.** A URL-mode question must be `https:` (`http:` only on a loopback host), without credentials, at most 2,048 characters; anything else fails the call. The copy shows `Opens: <origin>` on its own line. It is sent in URL mode only to a 2026-07-28 client that declared `elicitation.url`; any other client (and the R28 legacy shim) gets a form with the link as inert text and a single `done` checkbox.
7. **Legacy clients.** R28 applies unchanged: without `compat.legacyElicitation` a 2025-era client gets a `protocol` error naming 2026-07-28 and saying the call needed to pass on a question; with it, the shim carries the question in its form shape.
8. **Not forwarded.** Sampling and roots (Q2); more than 4 questions in one round; a request that is not an elicitation; a server state over 16 KB; for a source given by URL, a server state that would need credential redaction (S1: it would otherwise be sealed into a blob). Each fails the call in the `upstream` phase with the refusal hint.

## 7. Architecture

Nine components, cleanly separable for parallel workstreams:

**Introspector** — connects to the wrapped server (instance or remote), reads `tools/list`, annotations, and `instructions`, maintains the tool catalog. It holds one connection per alias: one under the default alias for `wrapMcpServer`, one per source for `wrapMcpServers` (§6.9); that per-alias connection map is also the seam per-principal upstream auth will reuse (§12.4). **Typegen** — produces `@astral-mcp/tools` runtime bridge + `.d.ts` from the catalog (JSON Schema → TypeScript). **Sandbox runtime** — `@sebastianwessel/quickjs` lifecycle, module mounting, caps, interrupts, marshaling. **Machine host** — evaluates the module, validates the contract, drives the actor, translates `toolCall` effects into host-side execution or suspension, injects result/verdict events. **Policy engine** — annotation defaults, the approvals mode (R49) and developer overrides; decides auto/ask/deny per resolved call. **Blob sealer** — snapshot packaging, AEAD, versioning, verification. **MRTR adapter** — maps suspensions to `InputRequiredResult`, parses `inputResponses` on retry, enforces trip caps; owns the MRTR vocabulary (`mrtr/protocol.ts`); the catalog projection builds its single `input_required` and reads its verdict through that same module. **Catalog projection** — search/describe over the catalog (per box and across boxes on a multi-server facade, R43) plus `call_tool`'s structural validation and canonical request hashing; reuses the policy engine, sealer and MRTR adapter. **Upstream auth** — for sources given by URL (§6.10): Projection's `OAuthClientProvider`, the device and authorization-code flows, the loopback listener, the token store, and each box's locked/unlocked state. It builds the sign-in elicitations and `signin` blobs through the sealer and the MRTR adapter, and the introspector reaches it through the per-alias connection map.

Two modules sit beside them: the MCP Apps dashboard (D5) and the workflow prompts (D8).

Dependency notes: pin XState v5.x exactly (snapshot compatibility across minor versions must be verified in CI before bumping); pin the quickjs-ng WASM variant; target the 2026-07-28 TypeScript SDK stable line.

## 8. Key flows

**Happy path, no writes.** Client calls `execute_machine`. Validation passes; machine runs; all tool calls are read-only and execute inline; machine reaches final state within budget; result returns as `resultType: complete`.

**Single approval.** Machine emits a gated `toolCall`. Host snapshots the actor, seals the blob, returns `input_required` with one elicitation. Client shows the prompt; user approves; client retries with the response and echoed blob. Library verifies (R21), restores, executes the write, injects `TOOL_RESULT`, machine runs to completion.

**Denial with fallback.** As above, but the user declines. `TOOL_DENIED` is injected; the machine transitions to its authored fallback branch (e.g. record "skipped", continue) and completes. The final result includes a per-call approval audit trail.

**Batched approvals.** A parallel state gates three writes; one `input_required` carries three keyed elicitations; the retry carries three verdicts; each maps to its own event.

**Direct call, read-only.** Client calls `search_tools`, then `describe_tool({ name: "read_file" })`, then `call_tool({ name: "read_file", args })`. Policy is `auto`; the call executes inline; the result is `{ status: "ok", tool, output }` in one round trip.

**Direct call, approved.** `call_tool({ name: "write_file", args })`. Policy is `ask`; the adapter seals a `call` blob binding the canonical request, returns `input_required` with one elicitation; the user approves; the client retries with the echoed blob; verification passes (R21); the recorded args execute; `{ status: "ok", ... }`. A decline returns `{ status: "declined" }` and nothing executes.

**Cross-server workflow.** On a facade wrapping `github` and `fs`, one machine reads `github.get_issue` (policy `auto`, runs inline) and writes `fs.write_file` (policy `ask`). The host routes each call by alias; the suspension's single elicitation is titled `Approve (fs): …`, reads `What fs says it does: …` and has the footer `Tool: fs.write_file · workflow step "…"`; the blob binds the facade's server-set identity under the multi-server key domain (R41), so it resumes only on a multi-server facade wrapping the same servers under the same aliases.

**First use of a server that needs sign-in.** A facade wraps `github` by URL, and no token is stored, so the box comes up locked: the shelf reads `github — sign-in required`. The model calls `search_github`. The authorization server supports the device flow, so Projection starts one and returns `input_required` with a URL-mode elicitation: `Sign in to github (api.githubcopilot.com)`, `You'll be sent to github.com`, the code, and a `signin` blob carrying the sealed device code. Every sign-in host is on `github.com`, the issuer's host, so the R61 sign-in host rule passes. The client retries when the user accepts. Projection finds no token in the store, holds the retry and polls the token endpoint at the server's interval; the user finishes signing in within the hold, so Projection gets the tokens and stores them in the OS credential store. (Had the 25-second hold ended first, the request would have re-suspended with the same link and code.) It then introspects the box and answers the original search. A later `call_tool` to a gated `github` tool asks for approval as usual.

**A wrapped server asks a question.** A facade wraps `crm` with `upstreamElicitation: 'forward'`. `call_tool({ name: "crm.export" })` runs (read-only); the server answers `input_required` asking which account. Projection returns its own `input_required`: one form, `Question from crm (not an approval)`, the server's words quoted, the schema allowlisted, and an `upstream_input` blob carrying the call and the server's `requestState`. The user answers; the retry re-issues `crm.export` with the answer and the server's state; the server completes, and the result is `{ status: "ok", ... }`.

**Self-heal.** Submitted code uses v4 `Machine()` syntax. Validation fails in ~tens of milliseconds; `isError` result with phase `validate` and a v5 hint returns; model rewrites; second call succeeds.

**Expiry / tamper.** Retry arrives after TTL or with a modified blob: verification fails with a structured `blob_verification` error; no side effects executed.

## 9. Security invariants

S1. The tools bridge is the only I/O channel out of the sandbox (no fetch, no host FS, no env beyond an explicit allowlist). On a multi-server facade the bridge reaches every box, still only through the host's per-alias executor, and the client still sees only Projection's tools (R1), never any wrapped server's. Upstream credentials never enter the sandbox, a blob, a log, stderr, an error message or any model-visible surface: access tokens, refresh tokens and client secrets live only in the token store and the host-side transport (R59). Device codes and PKCE verifiers exist only sealed (R56, R53). Authored code names tools, and the host-side executor makes the authenticated call. A credential the MCP client presents to Projection is never forwarded upstream (R61).

S2. No gated tool call ever executes without a verified approval verdict bound to that exact call (name + args captured in the sealed `pending` map — the approval authorizes the recorded args, not whatever the resumed machine asks for next). On a multi-server facade the recorded name is qualified (R40), so the approval binds the box as well as the tool.

S3. Blobs are authenticated and encrypted; clients carry them but can neither read nor alter them.

S4. `codeHash` binding prevents resuming a snapshot under different code. For `call_tool` the same field binds the blob to the canonical request as a coherence check (the approval itself is bound by `pending`, S2), and `kind` prevents a blob minted by one tool from being opened by the other.

S5. Annotations from third-party wrapped servers are untrusted hints; unannotated tools default to `ask`. They are never relayed to the host as a directly listed tool's annotations: those are derived from Projection's decision (R35). On a multi-server facade box aliases and descriptions are host-controlled; server text that reaches a box surface — the shelf line, the `search_<alias>` description, the box overview — is neutralized and capped (R43, R44). A hostile server cannot name a tool into another box (its names are always prefixed with its own alias, R40), shadow another box's policy (overrides are keyed by qualified names, R42), outrank another box's tools in `search_tools` for that box's alias (an alias token scores by box, never by text, R43), or be suggested for a name qualified with another box's alias (R40). Blobs never cross between single- and multi-server facades, whatever identity a server reports (R41). Under `approvals: 'destructive-only'` (R49) a non-read-only tool that declares `destructiveHint: false` runs without approval: this extends the trust Projection places in `readOnlyHint` to `destructiveHint: false`, and a hostile server can mislabel a damaging tool, so integrators enable the mode per source, for servers they trust. Sign-in data from a wrapped server is untrusted as well: its protected resource metadata, its authorization server's metadata, `error_description` text and user codes. Endpoints must pass the R61 discovery, issuer, HTTPS and sign-in host checks: a server that names a legitimate but unrelated identity provider fails, because every place the user is sent must share the validated issuer's host unless the integrator allowed it (`oauth.signInHosts` or an explicit endpoint override). User codes must match a fixed character set; error text is reduced to the OAuth `error` code and a neutralized, capped `error_description`. A hostile upstream cannot redirect a token to another resource (R61), and a token never appears in anything it can read back (R59).

S6. Approval text is derived from server-side data (the catalog entry's title, first description sentence and tool id) and the call's resolved arguments after the redaction hook. The only model-authored fragments are the argument values and the requesting state name, both rendered as inert quoted data. The model can never write prose into an approval prompt. On a multi-server facade the copy names the box by its host alias in the title, purpose line and footer (R46), never by a server-reported name. A forwarded server question (R64) is never approval copy: its first line names the box and says it is not an approval, the server's words appear only as quoted, neutralized lines under an attribution, its form passes the elicitation-primitive allowlist with every approval look-alike label, option or field name marked as the server's text and the approval forms' own field names dropped (R64.5), and answering it re-issues an already-authorized call and approves nothing. Sign-in copy (R55) is assembled only from host-controlled parts and validated values: the alias, the source URL's host, the validated issuer's host, and a user code checked against a fixed character set. The URL is rendered as inert text wherever it is not the URL-mode `url` field. No server-authored prose appears in it.

## 10. Success metrics

First-attempt valid-machine rate ≥ 60% and ≤ 2 attempts to valid ≥ 90% (measured against a benchmark suite of task prompts across 3 frontier models; the live benchmark runs one model per invocation over 4 file-server tasks with coarser gates). Validation latency p95 < 250 ms (not currently measured). Suspend→resume overhead (blob seal + verify + rehydrate) p95 < 100 ms. Zero gated executions without a matching verified approval in adversarial test suite. Median blob size < 8 KB on benchmark workflows.

## 11. Resolved questions

Q1. Scratch FS across suspensions — no FS surface at all (R9); scratch FS is stretch (§12.3).
Q2. Mid-run sampling requests — out of scope; sampling is deprecated, and the event protocol leaves room for new event kinds. A wrapped server's own sampling and roots requests are refused on every box; its elicitation is forwarded only on boxes that opt in (R64).
Q3. Snapshot migration across XState upgrades — none; strict `libv`/`xstatev` rejection (R20/R21). Blobs are short-lived, so a deploy fails the few in-flight workflows with a clean `blob_verification` error and the model re-runs.
Q4. Should `discover_apis` expose resources — yes, `resource_link` blocks backed by `resources/read` (R3).
Q5. Multi-tenant key derivation — a single developer-supplied key with the R22 rotation window; per-tenant HKDF revisits if a hosted deployment exists.
Q6. Cap machine complexity at validation — yes, a static state-node count (default 100, max 1 000, R12); runtime event caps remain the true safety net.

## 12. Stretch goals (the current architecture must not preclude them)

### 12.1 MCP Apps rendering

The 2026-07-28 spec ships MCP Apps (server-delivered HTML in a sandboxed iframe) as an official extension. **Shipped:** a static, library-authored workflow dashboard (`ui://projection/dashboard.html`, declared through `execute_machine`'s `_meta.ui.resourceUri`) that renders output, audit trail, logs and structured errors for app-capable hosts (D5); it is a compile-time constant with no model-authored code and no host capabilities. **Stretch:** rich approval previews (a diff or summary of a pending write instead of a bare schema form), blocked until the spec gives an `input_required` result a vehicle for an app reference, and SSR of model-authored UI (`@sebastianwessel/quickjs` can plausibly run `react-dom/server`). Design constraint decided now: UI-rendering code has zero access to the tools bridge and executes in a separate VM instance, so rendering can never become an approval bypass. `execute_machine` MAY later accept an optional `ui` argument.

### 12.2 Multiple wrapped servers

Promoted to requirements: §6.9 (R39–R49; DECISIONS D16, D17). Still out of scope: per-principal upstream auth (§12.4 — the per-alias connection map is the seam it will reuse; single-principal sign-in is §6.10), adding or removing servers after wrap, retrying a skipped optional source, and `tools/list_changed` handling beyond today's. Approval batching across boxes within one suspension is the opt-in R15 batched layout; batching across separate `call_tool` requests or separate suspensions is not (D25).

### 12.3 Scratch filesystem

Expose the sandbox's virtual FS to authored code as ephemeral per-segment scratch, with a size-capped FS delta optionally serialized into the blob for cross-suspension persistence. Deferred because "all state in context" is a simpler contract for the model and keeps blobs small; revisit if benchmark workflows show context bloat from large intermediate data.

### 12.4 Per-user upstream OAuth

**Promoted to requirements:** single-principal, just-in-time upstream sign-in (§6.10, R50–R62; DECISIONS D19). It covers sources given by URL, locked boxes, sign-in as an MRTR suspension, the device flow (phase 1) and the loopback authorization-code flow (phase 1b), and a token store (the OS credential store through `@napi-rs/keyring` by default — macOS, Linux and Windows — pluggable through `WrapOptions.tokenStore`). The constraint this section used to hold, that **upstream credentials never enter the sandbox, a blob, a log, an error message or any model-visible surface**, is now normative in S1 and R59.

**Integrator-owned auth is unchanged.** An integrator can still connect an SDK `Client` with its own auth provider on the transport (client-credentials grant, a provisioned refresh token, a static token) and wrap it. For such a `Client`, upstream auth expiry surfaces as an ordinary `TOOL_ERROR` event, and token refresh is the transport auth provider's job. It remains the path for everything listed below.

**Still out of scope.**

1. **Per-user and multi-tenant principals.** On-behalf-of access means each end user's own identity reaches the upstream (user A's GitHub, not one shared sign-in). The introspector holds one connection per alias (§6.9), made at wrap time or at unlock (R54). Per-user auth needs connections resolved per principal at call time, and per-principal resolution extends that per-alias map rather than adding a second one. Token-store keys already carry a principal component, fixed at `local` in phase 1 (R62), and sign-in-as-suspension (R55) carries over unchanged.
2. **Principal-bound blobs.** An approved blob must resume only under the principal that approved it, or user A's approved workflow could run under user B's token. The plan is to adopt the SDK requestState codec's `bind` concept (deferred in DECISIONS.md D1). That is a blob-format change, gated on the fuzz and tamper suites and a version bump.
3. **Hosted (non-loopback) redirect URIs** for the authorization-code flow. §6.10 has the device flow, which works in hosted deployments, and the loopback redirect (phase 1b), which works locally (R53).
4. **Secret references for static tokens**, such as a keychain item or a secret-manager reference named in configuration and resolved by Projection. Until then a static token is the integrator's `Client`'s business, and it is never written into an MCP configuration file.
5. **Credentials in a source URL**, such as an API key in the query string (R50). The URL is configuration, not a secret.

Token residence for multi-tenant deployments keeps the earlier preference: a server-side store keyed by principal (R59's `TokenStore`, shared), chosen over serializing refresh tokens into the AEAD blob. The blob option is architecturally purer, but it makes the client a courier of its own upstream credentials and stretches revocation windows. It stays rejected unless an adversarial review overturns this.

## 13. Verification and test plan

**Smoke-test matrix.** Source candidate servers from the Glama directory (https://glama.ai/mcp/servers) and pin a narrow initial set of three, chosen for shape diversity rather than coverage — the long-term goal is "any server"; the goal for these three is "flawlessly":

1. **Official filesystem reference server** — `@modelcontextprotocol/server-filesystem`, pinned, spawned over stdio; well-annotated, genuinely destructive writes (delete/move). Exercises annotation-driven policy and destructive-warning copy (`packages/harness/test/smoke/filesystem.test.ts`).
2. **GitHub MCP server** — a large remote API surface, rich JSON Schemas, mixed read/write. Stresses typegen fidelity and catalog size. Live and opt-in (`PROJ_LIVE_GITHUB=1` plus a token; `github.live.test.ts`).
3. **A SQLite server** — `mcp-sqlite`, pinned, spawned over stdio: a fully unannotated server whose `query` tool takes opaque SQL: exercises the default-`ask` posture (S5) and developer overrides (`auto` for a vouched-for read, `deny` for `query`), and proves the policy engine copes with tools whose safety isn't knowable from annotations (`sqlite.test.ts`).

A fourth smoke test, `pack-install.test.ts`, packs the library with `npm pack`, installs the tarball into a fresh project and runs a machine end to end — the only check that catches works-in-workspace, broken-when-published bugs. R37 (catalog scale) is covered only by synthetic-catalog tests; the one smoke server over the threshold (GitHub) is live-only.

**Catalog projection cases** (§6.8; `packages/projection/test/catalog/call.test.ts` and `test/integration/call-tool.test.ts`), all asserting that nothing executes: a `call` blob replayed to `execute_machine` and a `machine` blob to `call_tool` (R36 kind check); an approved `call_tool` retried with different `args` (binding-hash mismatch); a retry whose `inputResponses` omits the key (treated as declined); and `call_tool` on a `deny`-policy tool. Plus approve-then-replay within TTL, which re-executes the call (D4 known limitation, mirroring `packages/harness/test/replay.test.ts`); the assertion flips to exactly-once when a replay cache is configured (R38).

**Multi-server cases** (§6.9), asserting nothing executes where a gate should hold: an approved `fs.write_file` blob retried as `github.write_file` (binding-hash mismatch); a blob resumed on a facade with a different alias mapping, server set or server version (R41); a single-server blob opened by a multi-server facade and the reverse, under the same key and with a wrapped server whose reported name spells the other facade's identity, failing authentication (R41 key domain); a hostile server declaring a tool named `github.delete_repo` lands as `fs.github.delete_repo`, is gated by the facade policy's `fs.` keys, and its approval footer reads `Tool: fs › "github.delete_repo"` (R40, R42, R46); a hostile `fs` server whose names and descriptions repeat `github` does not outrank the `github` box's tools for the query `github issue` in `search_tools`, and `github.delet_repo` suggests only `github` tools, never `fs.github.delete_repo` (R40, R43); an `options.policy` key that is unqualified or names an unconfigured alias fails the wrap, one for a skipped optional box is ignored (R42); a non-optional source that fails or exceeds `introspectTimeoutMs` fails the wrap and closes every connection Projection opened while a caller-owned `Client` stays open, an optional one is skipped and reported (R47); the same source under two aliases, an unknown `ServerSourceConfig` key, the alias grammar, the reserved `default` and `tools`, a reserved-word alias (`delete`) whose `.d.ts` type-checks, and the 16-source and 4000-tool bounds (R39, R45, R48); a cursor from `search_fs` replayed to `search_github` or `search_tools` (R43). Typegen goldens for a two-box `.d.ts`; `wrapMcpServer` goldens stay byte-identical.

**Approvals-mode cases** (R49), single- and multi-server: under the default `every-write` nothing changes; under `destructive-only` a non-read-only tool declaring `destructiveHint: false` runs without approval, while a missing, `true` or non-boolean `destructiveHint` still asks; a per-tool `ask` or `deny` beats a relaxed mode and a per-tool `auto` still runs; a per-source value beats the global one in both directions; postures, `.d.ts` doc comments and the overview reflect the resolved decision; a malformed value fails the wrap with a `validate` error.

**Upstream sign-in cases** (§6.10). These run offline against a fake protected resource (an MCP server answering 401 with `WWW-Authenticate`, plus its RFC 9728 metadata) and a fake authorization server (RFC 8414 metadata and authorization, device, token, registration and revocation endpoints, with per-test switches). Every case asserts that nothing executes where a gate should hold. Cases marked _(phase 1b)_ land with phase 1b.

- **Registration (R52):** `oauth.clientId` used as given, with no DCR; no registration path at all, which ends directly in an `auth` error naming `oauth.clientId`, with no elicitation and no secret. _(phase 1b)_ Dynamic client registration, persisted in the store, with no second registration after a restart; CIMD when advertised.
- **Device flow (R53, R57):**
  - a token already in the store is found before any poll;
  - the hold: approved within it; still pending when it ends, then re-suspended with the same `elicitationId` and `exp`, `trips` advanced and `trip` unchanged; polls spaced at the interval, with `slow_down` adding 5 seconds;
  - re-suspension past the R12 round-trip cap, ending only at the flow's expiry (`auth`);
  - denied (`sign_in_declined`; _(phase 1b)_ `TOOL_DENIED` in a machine); expired (`auth`);
  - the device authorization request authenticated when `oauth.clientSecret` is set;
  - scopes: `oauth.scopes` sent as given, else the protected resource metadata's `scopes_supported`;
  - _(phase 1b)_ a machine whose audit holds an executed gated call never gets `sign_in_required`.
- **Sign-in host (R61):** an authorization, device-authorization or verification URL on a host other than the issuer's is an `auth` error; an explicit endpoint override or an `oauth.signInHosts` entry admits it; the message names the alias, the resource host and the issuer host.
- **Errors (R57):** an `auth` error carries only library copy, an OAuth `error` code matching `^[a-z_]+$` (a code that does not match is dropped) and a neutralized, capped `error_description`, never SDK or keyring error text.
- _(phase 1b)_ **Authorization code + PKCE (R53, R61):** the round trip through the loopback listener; a callback with a forged, replayed or expired `state` refused; a valid `state` with an `error` ends the flow and closes the listener; a listener bound to `127.0.0.1` only and closed after use, after TTL and on `close()`; `Cache-Control: no-store` and `Referrer-Policy: no-referrer` on every response; S256 enforced; an issuer mismatch on the callback refused.
- **Locked boxes (R54):**
  - the shelf, search results, `.d.ts` and overview while locked, with an identical tool list before and after unlock;
  - the `search_<alias>` description fixed at wrap time, byte-identical before and after unlock;
  - global `search_tools` and `discover_apis` do not suspend;
  - `describe_tool` and `call_tool` suspend, then proceed after sign-in, and a gated call still asks for approval;
  - a configured `deny` returns `denied_by_policy` without sign-in;
  - a machine `toolCall` gets a `TOOL_ERROR` naming the box's search tool; _(phase 1b)_ it suspends and proceeds after sign-in;
  - a single-server locked facade;
  - an `UpstreamSpec` with the catalog projection off is a `validate` error; _(phase 1b)_ `discover_apis` suspends instead;
  - a token stored by another instance unlocks without asking, including on a resume that lands on an instance where the box is still locked;
  - a non-401 introspection failure still fails the wrap;
  - R48 limits at unlock.
- **Re-lock and refresh (R58, R59):**
  - a 401 mid-request re-locks the box and suspends; a 401 in a machine is a `TOOL_ERROR` (_(phase 1b)_ a sign-in suspension);
  - refresh on expiry, and a rotated refresh token is saved;
  - two facades sharing one store: a token refreshed or stored by one is used by the other without a second refresh, and re-lock never deletes a record that changed since the failed token was read (compare-and-delete);
  - `insufficient_scope` as an `auth` error; _(phase 1b)_ step-up;
  - `signOut` deletes and re-locks; _(phase 1b)_ it also revokes.
- **Provider (R58):** `redirectToAuthorization` never opens a browser or starts a flow; concurrent device-code redemptions for two boxes do not cross; an error other than the three sign-in errors is not treated as an auth failure; a redirect to another origin is not followed.
- **Blobs (R56, R60):** a `signin` blob opened by another tool, or by the same tool with a different request; the verification order, including an expired blob opened at the wrong tool (`blob_verification`) and at its own tool (`auth`); tamper and replay with a replay cache configured; a blob minted while locked verifies after unlock; `url:` identities never collide with any `name@version`.
- **Fallback shapes (R55, R28):** URL mode (the embedded `elicitation/create` request, only for a client declaring `elicitation.url`), form only, no elicitation, and the legacy shim. In the no-elicitation case: a second request on the same instance gets the same link and code, and the next request after the user signs in redeems the pending flow and proceeds.
- **No credential leaks** (S1, R59): grep-style assertions that a distinctive access token, refresh token, client secret, device code and PKCE verifier never appear in any tool result, `structuredContent`, decrypted blob payload, captured log, stderr (the SDK's `console.warn` output included), error message, elicitation, or `.d.ts`/overview resource, across every case above.
- **Token store (R59):**
  - a round trip of a large record (at least 4 KB) through the keyring adapter;
  - the account is the SHA-256 of the store key, and no URL or query string appears in the entry's metadata;
  - every write is read back;
  - fallback to the in-memory store, with exactly one warning, when `@napi-rs/keyring` is absent or fails to load;
  - a hung store operation times out after 5 seconds and falls back;
  - no secret in argv, logs or errors, and keyring error text never surfaced.
- **Unchanged outputs:** `wrapMcpServer` and `wrapMcpServers` goldens and blobs over pre-built sources stay byte-identical.

**Live sign-in smoke** (phase 1; manual and interactive, opt-in with `PROJ_LIVE_GITHUB_SIGNIN=1` plus `PROJ_GITHUB_OAUTH_CLIENT_ID`; never in CI, because a human signs in). Against GitHub's remote MCP server, `https://api.githubcopilot.com/mcp/`, with an OAuth app the tester registers, with "Enable Device Flow" ticked and no client secret used. GitHub's server has no dynamic client registration (github/github-mcp-server#1404). Its protected resource metadata names `https://github.com/login/oauth`, whose metadata advertises `device_authorization_endpoint` (checked 2026-10-29), and its issuer, endpoints and verification URI are all on `github.com`, so the R61 sign-in host rule passes. The configuration is `oauth: { clientId, scopes }`, with the scopes set explicitly (for example `repo`) rather than left to metadata. The run:

1. Wrap with an empty token store; the box comes up locked.
2. `search_github` shows the device-code elicitation, naming `api.githubcopilot.com` and `github.com`; sign in in the browser.
3. The retry holds, unlocks the box and returns results, and the token lands in the OS credential store.
4. A read-only `call_tool` succeeds.
5. A write asks for approval.
6. Restart, and the box comes up unlocked from the store.
7. `signOut` re-locks the box.

The smoke also records two behaviours to verify, not assume: whether GitHub accepts, ignores or rejects `offline_access` among the requested scopes, and whether it issues a refresh token.

**Integration docs.** `docs/server-authors.md` gains an "Upstream authentication" section, written with the implementation rather than ahead of it.
