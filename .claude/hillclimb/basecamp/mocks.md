# Basecamp: mock fidelity (`mocks`)

Branch `basecamp-mocks`. Goal: every fake server in `packages/harness` answers the way the real server it imitates answers, so that a task's difficulty comes from the task and not from the fake.

## What was built

- **GitHub fake** (`src/eval/github-fake.ts`, `multi-hard-github.ts`). I compared it tool by tool against the real server and rewrote the answers to the server's own shapes, error texts, paging and validation. Every tool that is not modelled now gets a realistic answer, and `{ok:true}` is gone everywhere:
  - an unknown repository gets a 404;
  - an unmodelled read gets `[]`, an empty search page, or a 404;
  - an unmodelled write gets the real success shape.
- **Host view** (`modes.ts` `toolResultText`). An embedded text resource is now shown to the model as its text, as a host shows it. GitHub's `get_file_contents` sends files that way.
- **Workplace fakes** (chat, tracker, errors, docs, mail). I judged these on realism and fixed 10 gaps, each with a test in `test/eval/workplace-fidelity.test.ts`.
- **MongoDB assumption.** `find` without a `limit` returns 10 documents, not the 100-document cap. This is now documented (`MONGODB_FIND_DEFAULT_LIMIT`) and pinned by a test against the snapshotted catalog.
- **Graders and goldens** were updated wherever fidelity moved the right path (details below).

Run the tests with `pnpm --filter @astral-mcp/harness exec vitest run test/eval/github-fake.test.ts test/eval/multi-hard-github.test.ts test/eval/workplace-fidelity.test.ts test/eval/mongodb-world.test.ts`. `pnpm run check` is green.

## Fidelity sources

- **GitHub.** The fixture is a dump of the hosted build `github-mcp-server/remote-7eab724b…`, taken on 2026-10-10. That commit is not public: the GitHub repo answers "not our ref".
  - I scored public commits by how many of the fixture's descriptions and schemas they match byte for byte. The best match is **github/github-mcp-server `eb47a99` (2026-10-08, v2.0.0 plus two fixes)**.
  - Remaining drift from that commit:
    - the remote's `x-mcp-header` schema annotations;
    - six remote-only tools with no public source: `semantic_issue_similarity_search`, `get_copilot_space`, `list_copilot_spaces`, `github_support_docs_search`, `run_secret_scanning`, `check_dependency_vulnerabilities`;
    - the `get_job_logs` annotations.
  - The host speaks a protocol older than 2026-07-28, so the server's legacy era applies (`pkg/inventory/server_tool.go:448`, `typed_output.go:251`): no output schemas, and no `structuredContent`. Each result is one compact JSON text block. The exceptions are `get_file_contents` (text plus an embedded resource) and the review writes, which answer in plain text.
  - Citations in the code are written as `upstream <file>:<line>`, relative to `pkg/github/` at eb47a99.
- **MongoDB.** The vendored `mongodb-mcp-server` 3.2.1 (`@mongodb-js/mcp-tools-mongodb` `tools/read/find.js`: `limit … .default(10)`; `mcp-cli` `userConfig.js`: `maxDocumentsPerQuery` default 100).
- **Filesystem.** The real `@modelcontextprotocol/server-filesystem` 1.0.0. The harness's claims about it (14 tools, parent directories must exist) hold. Nothing to fix.
- **Workplace.** These are generic services, judged against the closest public API docs: Slack conversations.replies and users.profile.get; Linear's MCP; Sentry's MCP and API; the Gmail search operators and messages.modify; Notion's database query and errors. A subagent wrote the links from memory and did not re-fetch them.

### Not changed (judged plausible or too risky)

- **Tracker paging (10 per page, max 50).** This matches a popular tracker MCP (mcp-atlassian `jira_search` defaults to 10, max 50). Linear's own API defaults to 50. I kept 10, since it is plausible and it carries wp-urgent-open's intended difficulty.
- **Chat history (10 per page).** Plausible for Slack MCP servers. Kept.
- **Sentry `search_issues` cursor**, extra `is:` values, the four Notion tools that are missing, and `reply_to_thread` with a reply's ts. Either the real behaviour is uncertain, or the change would alter a frozen surface.
- **Offline `catalogServer`** (`src/eval/offline/catalogs.ts`) still answers `{"ok":true}`. It only lists tools and is never called.

## Grader and golden changes (every correct path accepted)

- `listsOpenPrs`: `state: 'all'` now counts. It lists the open PRs too; this affects list-open-prs and cross-open-prs-to-notes.
- branch-off-main-or-default (`knowsNoMain`): "has seen every branch" now means all 64, i.e. all three pages or `perPage ≥ 64`. An explicit `master` was always accepted. In calibration Haiku learned the default from the root listing's `html_url` (`/blob/master/`).
- cross-version-to-branch: a valid `from_branch` is any real branch name (case-sensitive), not just one of the six.
- hard-chain-failing-owner and hard-branch-failing-checks:
  - `steps` now include `get_job_logs`;
  - N for the chain task is 5 → 6, so its budget is 20 → 22;
  - the goldens read the job logs. Graders read answers and side effects, so every log path (`job_id`, `failed_only`, `actions_list`) passes.
- Goldens and tests moved from page 2 to page 3 for the release branches (global-version-branch, branch-from-latest-release-branch).

## Fixes that could have changed past round outcomes

These ran in every projection round on these tiers.

1. **Multi-hard check-run summaries.** They gave away the failing file. Real check runs have no output, so the file is only in the job log. Past passes on **hard-chain-failing-owner** and **hard-branch-failing-checks** were easier than reality by one or more hops.
2. **Multi-hard free-text PR search.** An empty-word bug made every PR match any query. That made search useless for **hard-comment-export-prs** and the newest-PR lookup, which pushed models toward listing.
3. **Branch paging (3 → 30 per page) and the `create_branch` error that named `master`.** The error made **branch-off-main-or-default** and **cross-version-to-branch** one-step recoveries. Paging changes the depth for **branch-from-latest-release-branch** and **global-version-branch** from page 2 to page 3. With four PRs on one page, **cross-open-prs-to-notes** now has nothing to page (easier).
4. **Unmodelled tools answering `{ok:true}` in the basic and hard tiers.** basic **read-readme** returned `{"ok":true}` as the README. That is graded on the call, but any verify or answer check, or a code-mode script that parsed the result, saw garbage.
5. **`get_file_contents` file shape.** It was JSON `{content}`; it is now text plus an embedded resource. Projection's "parsed JSON for machines" path saw a different result type before. This affects **read-lowercase-readme**, **box-readme-github** and **read-readme**.
6. **`issue_write` returning the issue.** It is now `{id,url}`, so code that read `.number` from the result now has to parse the url. This affects the multi-hard creates and **upsert-issue-missing**.
7. **list_issues rejected lowercase `state`.** This cost an extra failed call in any mode, and made things harder than the real server.
8. **Workplace.** Assignee lookup by ID or name was too strict (harder): wp-error-owner-thread, wp-review-queue. Sentry total counts were too generous (easier): wp-degraded-counts. Gmail operators were ignored (harder): wp-customer-reply.

## Open problems

- **Unsupported search qualifiers in multi-hard.** These still get an invented 422 (`… not supported by this repository's search`). Real GitHub applies qualifiers such as `milestone:`, which the fake does not model. Honest about the limit, but not real text.
- **Validation errors** use the TS SDK's wording (`Input validation error: … must have required property`). The real server says `validating "arguments": …` or `invalid arguments: normalize tool arguments: missing required parameter: X`. The information is the same; the words differ.
- **go-github's error format.** `METHOD URL: 404 Not Found []` and the 422 layout come from the server's error helper plus my recollection of go-github's `ErrorResponse.Error()`, which is not vendored there.
- **GraphQL `issues(labels:)` matching any** of the labels is GitHub's documented behaviour. I could not confirm it in the server source, which passes the list through.
- **Remote-only tools** have no public source, so their answers are guesses: `semantic_issue_similarity_search` returns `[]`, and the rest get the generic unmodelled answers.
- **Unmodelled writes without a known shape** return MinimalResponse `{id,url}`. That is the server's most common write shape, but not verified per tool.
- **global-version-branch** is unsolved in direct mode without box descriptions (see above). It needs a task-design decision, not a mock fix.
